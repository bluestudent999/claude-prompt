# 任務拆解與排程標準 (Task Breakdown & Sequencing)

> 本文規範企劃階段如何把一份 Business Spec 拆成**一顆顆有邊界、有依賴、大小可控的 TASK**,並產出 Task Backlog。
> **這一層是企劃防止「開發 AI 上下文爆掉」的關鍵**:開發端拿到的是切好的工單,而不是一坨大 Spec。
> 由 `delivery-planner` agent 執行;產出經 `spec-reviewer` 審查後打 Baseline。

---

## 0. 為什麼需要這一層

開發 AI 的上下文會爆,幾乎都源於**輸入單位太大**(不是對話太長,那是 `context-discipline.md` 的事):

- 單顆任務觸及太多檔案 / 模組 → 一次要載入的程式碼超過視窗
- 任務沒有對映「只需讀哪段規格」→ AI 被迫通讀整份 Spec
- 任務沒有排序 → AI 不知道先做哪顆,一次抓一堆進上下文

**企劃層的職責**:切出**業務層級**的 TASK(feature / story 顆粒),不碰技術實作步驟(那是開發 planner 的 How)。切得好,開發 AI 每顆任務都能在單一乾淨的上下文裡完成。

---

## 1. 一顆好 TASK 的三大準則

### 1.1 垂直切片 + 單一職責 (Vertical Slice, Single Responsibility)
- 一顆 TASK 只交付**一個可獨立驗收的業務結果**。
- **禁止**把「資料結構 + API + 畫面 + 通知」全塞進一顆 TASK。
- 對照開發專案紅線:「一個 TASK 只做一件事」— 但**在企劃階段就先切好**。

### 1.2 對映最小規格切片 (Minimal Spec Slice)
- 每顆 TASK 必須標明 `Required Spec Sections`:完成它只需讀 Spec 的哪幾節 / 哪幾條 AC。
- 這是**上下文預算的核心欄位** — 讓開發 AI 精準載入,而非通讀。

### 1.3 尺寸受控 (Context Budget)
- 每顆 TASK 標一個尺寸級別(見 §3)。
- **硬規則**:預估為 `L`(大)的 TASK **必須再拆**,不得直接交付開發。

---

## 2. Task Backlog 格式(delivery-planner 產出)

存放於企劃專案的 `plan/<功能>/backlog.md`(或 Spec 文件末段)。結構如下:

```markdown
# Task Backlog: <功能名稱>

**對應 Spec:** plan/<功能>/spec.md
**Baseline:** ⏳ 未定案 / ✅ vN (YYYY-MM-DD)
**Delivery Planner:** delivery-planner agent

## 依賴關係圖 (DAG)

​```mermaid
graph TD
    T1[TASK-1 建立帳號資料模型] --> T2[TASK-2 註冊流程]
    T1 --> T3[TASK-3 登入流程]
    T2 --> T4[TASK-4 註冊成功通知]
​```

## 任務清單

| Task ID | 一句話目標 | Required Spec Sections | Scope 邊界(業務語言) | Depends On | Context Budget | AI 產出 | 人介入 | 對應 AC |
|---------|-----------|----------------------|--------------------|-----------|---------------|--------|-------|--------|
| TASK-1 | 定義帳號核心資料與狀態 | §1.4 R1–R3、§1.5 | 僅帳號本體;不含通知/金流 | — | S | XS | 1 確認 | AC-1, AC-2 |
| TASK-2 | 使用者可完成註冊 | §1.3 Flow-A、§1.6 AC-3~5 | 註冊表單 + 驗證;不含第三方登入 | TASK-1 | M | S | 2 確認 + 1 OQ | AC-3, AC-4, AC-5 |
| TASK-3 | 使用者可登入 | §1.3 Flow-B、§1.6 AC-6~7 | 帳密登入;不含 SSO | TASK-1 | M | S | 1 確認 | AC-6, AC-7 |
| TASK-4 | 註冊成功寄出歡迎通知 | §1.3 Flow-A step5、§1.5 通知失敗 | 僅通知;通道細節交開發 | TASK-2 | S | XS | ⏳ 等第三方(通知服務開通) | AC-8 |

**估算合計：** AI 產出 ≈ 2.5 人日｜人介入 4 確認 + 1 OQ + 1 外部等待
> 交期以**人介入**為主要依據，不是 AI 產出的加總（見 §3.5）。外部等待不可與其他 TASK 抵銷。

## 建議實作順序 (Sequencing)
1. TASK-1(無依賴,最先)
2. TASK-2 ‖ TASK-3(皆僅依賴 TASK-1,可平行)
3. TASK-4(依賴 TASK-2)

## Open Questions
- ✅ OQ-1: 是否支援第三方登入? → 本期 Out of Scope(PM 決議 2026-07-01)
- ➡️ OQ-2 (defer-to-dev): 通知走 Email 或站內信? → 技術問題,交開發 planner
```

### 欄位定義

| 欄位 | 說明 | 為什麼重要 |
|------|------|-----------|
| **Required Spec Sections** | 完成此 TASK 需讀的規格節 / AC 編號 | **開發 AI 只載入這幾節**,不通讀整份 Spec ← 防上下文爆炸的核心 |
| **Scope 邊界** | 用業務語言寫「包含 / 不含什麼」 | 防 Scope Creep;讓開發 AI 知道邊界在哪 |
| **Depends On** | 前置 TASK ID(可多個) | 構成 DAG;前置未完成禁止開始 |
| **Context Budget** | S / M / L 尺寸(見 §3) | L 必拆;讓 AI 每顆任務都塞得進視窗 |
| **AI 產出** | XS/S/M/L 粗量級(見 §3.5) | 容量感與排序;**非交期承諾** |
| **人介入** | 決策/確認/OQ/外部等待的次數與種類(見 §3.5) | **排程的真正依據** — AI 開發下交期由這欄決定 |
| **對應 AC** | 此 TASK 交付後要驗收的 AC 編號 | 可驗收、可追溯到 Spec |

---

## 3. Context Budget 分級(尺寸標準)

> 企劃無法精算 token,改用**可觀察的業務代理指標**估算顆粒。

| 級別 | 業務訊號(估算用) | 處置 |
|------|-----------------|------|
| **S(小)** | 單一實體 / 單一畫面 / 單一規則;對映 ≤ 2 條 AC | 直接交付 |
| **M(中)** | 一條完整 User Flow;對映 3–5 條 AC;跨 1–2 個業務概念 | 直接交付 |
| **L(大)** | 跨多條 Flow / 多個業務概念;對映 > 5 條 AC;Scope 邊界一句話講不清 | **必須再拆**,禁止交付開發 |

**硬規則:**
- 任一 TASK 估為 `L` → delivery-planner 必須拆成多顆 S/M,不得直接進 Backlog。
- 拆不動的 L(業務上不可分割)→ 標 `⚠️ 大顆粒` 並在 Backlog 註明理由,提醒開發端優先 `/strategic-compact`。

## 3.5 工時估算（前提：AI Agent 開發）

> **本組織的開發模式是「1 人 + AI Agent」，不是傳統人力編組。** 估算必須依此前提，
> 但**不是把傳統人天打個折就好** —— 打折會系統性低估，因為被壓縮的和沒被壓縮的比例完全不同。

### 3.5.1 三分法（估算的基本模型）

把一顆 TASK 的工作拆成三類，**分別估**：

| 類別 | AI 的影響 | 典型工作 |
|------|----------|---------|
| **A. AI 可壓縮** | **大幅縮短** | 寫程式、寫測試、boilerplate、查 API 用法、重構、寫文件 |
| **B. 不可壓縮（等人）** | **幾乎不變** | 需求決策、回答 OQ、規格 CONFIRM、review 判斷、驗收、跨團隊協調 |
| **C. AI 帶來的新成本** | **增加** | 切 TASK 與準備上下文、驗證 AI 產出是否真的對、走偏了拉回來 |

> **最關鍵的一句：交期由 B 決定，不由 A 決定。**
>
> 傳統估算裡 A 佔大宗，所以「AI 讓開發快 5 倍」聽起來成立。但 A 縮短後，**B 就浮上來變成關鍵路徑** —— 總交期通常只快 2 倍左右，而不是 5 倍。承諾前先想清楚這件事。

### 3.5.2 企劃層估什麼、不估什麼

| ✅ 企劃層估 | ❌ 留給開發 planner |
|-----------|-------------------|
| **`人介入`**：需要幾次人決策、幾個 OQ、預期 review 輪次 | 技術實作步驟的人日加總 |
| `AI 產出`：粗量級（供排程參考） | 精確工時 |
| 需要**等誰**（PO / 第三方 / 其他團隊） | 測試層級、token 估算 |

> **企劃層的估算是量級，不是交期承諾。**
> 開發端把技術步驟拆完、由下而上加總後，**以開發端的數字為準**。
>
> **實例（本組織）：** `crypto-node` 由上而下粗估 5.5 週，38 個實作步驟由下而上加總為 6.3 週 —— 該專案的企劃書明訂「以由下而上為準」。**由下而上一定比較高，而且比較準。**

### 3.5.3 Backlog 的兩個估算欄位

| 欄位 | 取值 | 意義 |
|------|------|------|
| **`AI 產出`** | `XS` ≤ 0.5 人日 ／ `S` ≈ 1 ／ `M` 2–3 ／ `L` > 3（**須拆**） | 粗量級，供排序與容量感 |
| **`人介入`** | 次數 + 種類，例：`2 確認 + 1 OQ`、`1 驗收`、`⏳ 等第三方` | **排程的真正依據** |

**硬規則：**
- `AI 產出` 估為 `L` → 與 `Context Budget` 的 `L` 一樣**必須再拆**。
- `人介入` 含 `⏳ 等外部`（第三方、其他團隊、法遵）→ 在 Sequencing 標為**日曆風險**，不可與其他 TASK 的等待時間相加抵銷。

### 3.5.4 最常被低估的四件事

1. **驗證成本** —— AI 一小時產出的東西，人可能要三小時才能確認它是對的。
   **專案沒有自動化測試 → 驗證成本再乘以 2。**（本組織實例：`sicbo` 無任何測試，L1 驗證只能靠回放留存影像逐張比對）
2. **第一次接觸的業務領域** —— AI 不知道你們的業務規則。同一個 Backlog 的**前 2~3 顆 TASK 會明顯慢**，之後才進入速度。估算時不要用穩定期的速率去估開頭。
3. **跨系統契約** —— 需要對方配合的，**交期由對方決定**，不是你的估算能控制。標 `⏳ 等外部`。
4. **決策等待** —— OQ 從提出到被回答的時間**不含在開發工時裡**，要在日曆上另外留。
   （本組織實例：`crypto-node` 開發 9.3 週，卻規劃 3 個月日曆，餘裕就是留給決策等待、聯調與意外）

### 3.5.5 不要做的事

| ❌ | 為什麼 |
|---|--------|
| 把 A 類的加速倍率套用到整顆 TASK | B 類沒有變快，會系統性低估 |
| 把多顆 TASK 的「人介入」當成可平行 | **同一個人**，那是序列的；AI 產出才可平行 |
| 把企劃層的粗估當交期承諾對外報 | 那是量級。交期以開發端由下而上的加總為準 |
| 沒有 OQ 就當作沒有決策成本 | 沒列出來的決策，會在開發到一半時冒出來，而且更貴 |
| 用「AI 很快」壓縮 review 與驗收 | 那正是 AI 開發**最需要**加強的一段 |

### 3.5.6 回填與校正（估算會準，是因為回填）

Backlog 完成後，回填每顆 TASK 的**實際** `AI 產出` 與 `人介入`，並記錄差異原因。

- 累積 10~20 顆後，校正本專案的估算係數。
- 對照開發端的 AIDD 指標（`估算 vs 實際工時`）交叉驗證。
- **沒有回填的估算，下一次還是猜的。** 這是估算能力唯一的來源。

## 4. DAG 與排序規則

1. **依賴必須無環**:TASK 依賴關係構成有向無環圖(DAG),出現環 → 表示切分錯誤,重切。
2. **前置未完成禁止開始**:對映開發專案的 Dependency Rule。
3. **標出可平行分支**:同層(依賴相同、彼此無依賴)的 TASK 標為可平行,讓開發端能獨立起 session、各自在乾淨上下文推進。
4. **關鍵路徑優先**:被最多後續 TASK 依賴的節點(如共用資料模型)排最前。

## 5. delivery-planner 的邊界(不越界到 How)

| ✅ 企劃層要做 | ❌ 留給開發 planner |
|-------------|-------------------|
| 切出業務層 TASK(feature/story) | 拆技術實作步驟(改哪個 class/method) |
| 標 Required Spec Sections | 指定受影響的程式檔案清單 |
| 標業務語言的 Scope 邊界 | 指定 Allowed Modules / package |
| 標 TASK 間業務依賴 | 標 commit 粒度 / 分支策略 |
| 標 Context Budget(業務尺寸) | 估 token / 測試級別 L1-L3 |
| 標 `AI 產出` 粗量級 + **`人介入`**(§3.5) | 技術步驟的人日加總(由下而上,以開發端為準) |

> 越界訊號:如果 delivery-planner 開始寫「新增 `XxxService.foo()`」「改 `application.yml`」,就是踩進 How,**停手**,那是開發 planner 的職責。

## 6. Quality Gate(delivery-planner 自檢)

Backlog 交 spec-reviewer 前,自檢:

- [ ] 每顆 TASK 都有 `Required Spec Sections`(無空白)
- [ ] 每顆 TASK 都有 `Context Budget`,且無 `L` 未拆
- [ ] 每顆 TASK 都有 `AI 產出` 與 `人介入`,且 `AI 產出` 無 `L` 未拆
- [ ] 含 `⏳ 等外部` 的 TASK 已在 Sequencing 標為日曆風險
- [ ] 依賴關係無環,已畫 DAG
- [ ] 每顆 TASK 對映至少一條 Spec AC(無孤兒 TASK、無漏接 AC)
- [ ] 每條 Spec AC 至少被一顆 TASK 覆蓋(反向檢查,無漏)
- [ ] Scope 邊界用業務語言,未寫技術實作
- [ ] 無 `⏳ 待決` OQ(否則不得打 Baseline)
