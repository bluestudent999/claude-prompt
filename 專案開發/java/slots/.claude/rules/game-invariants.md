# 工程不變量 I1 ~ I8（最高紅線）

> 這八條是**工程層面**的正確性定義：錢不會算錯地方、不會動兩次、事後查得到。
> **業務規則不在這裡。** 賠率怎麼算、線怎麼連、彩池怎麼觸發，一律讀 `plan/yummy/spec.md` §1.4。
>
> 這裡的每一條都必須有自動化測試，Code Review 以此為檢查清單。**違反 = block。**
> 這八條與業務規則的差別：業務規則你可以改（`plan-authority.md`），這八條不行 —— 改了就不是「對的軟體」了。

---

## 對照表

| # | 不變量 | 白話說明 | 破掉會怎樣 |
|---|--------|---------|-----------|
| **I1** | **後端權威**：盤面、中獎線、派彩金額一律由後端決定；後端不接受前端送來的結果類欄位 | 前端只能說「我要轉，下這麼多」，不能說「我中了多少」 | 玩家改前端就能自己決定中獎 |
| **I2** | **錢包唯一**：遊戲不得自建餘額儲存，只能透過錢包介面查／扣／派 | 錢在平台錢包裡，遊戲只是去動它 | 兩份餘額對不起來 |
| **I3** | **入帳不依賴前端**：派彩由後端自行完成，不得以「前端回報動畫播完」為條件 | 玩家動畫播到一半關瀏覽器，獎金照樣要進去 | 玩家斷線就吃掉獎金 |
| **I4** | **單局冪等**：同一局重複進來，錢只能動一次；重試必須用同一個識別碼 | 連點、網路重送都只結算一次 | 重複扣款或重複發獎 |
| **I5** | **金額用整數**：一律以最小幣別單位整數運算，禁止浮點數 | 錢不能用小數存 | 長期對帳出現無法解釋的尾差 |
| **I6** | **資金守恆可對帳**：任何有累積性質的池子（彩池等），`累計注入 − 累計派出 = 當前餘額` 任何時刻成立 | 錢不能憑空生出來或蒸發 | 池子被掏空或超額派獎 |
| **I7** | **開獎留痕可回放**：隨機來源、結果矩陣、中獎線、派彩、餘額前後值全部落盤 | 任何一局事後都能完整重演 | 客訴「我明明中了」時無法舉證 |
| **I8** | **試玩模式無真金流路徑**：v1 不得存在任何可通往儲值／提現／真實支付的程式路徑 | 試玩版連路都不能有 | 誤觸真金流，而法遵前置作業尚未進行 |

## 兩條特別容易漏的

### I3 的斷點在動畫裡

`spec.md` R-7 已經把這條訂為鐵則，理由值得再說一次：

參考站的觀察只證明**顯示上**的餘額在動畫後才更新 —— 那是視覺效果。
若把**實際入帳**綁在前端訊號上，玩家在動畫期間斷線就會吃掉獎金。

- 前端可以回報「動畫播完了」，但那**不能是入帳的唯一觸發**。
- 前端重複回報也不得重複入帳 —— 靠 I4 擋。
- 前端不得因為「還沒播完」而隱藏或修改金額。跑分只是視覺，數字來自後端。

### I4 在批量與特殊流程下最難守

批量遊戲連跑 100 局、免費旋轉序列、BONUS 選箱 —— 每一局、每一次派彩都要有自己的識別碼。
用「這一批」當識別碼，重試時會整批重算；用時間戳，併發時會撞。

## 使用方式

- **planner**：拆任務時標出會碰到哪幾條，每條配一個驗收測試。
- **payout-guard**：以 I2~I6 為檢查清單。
- **arch-guard**：以 I1 為邊界依據。
- **rng-rtp-reviewer**：以 I6、I7 為檢查清單。
- **Code Review**：改動觸及哪條，就要指出對應測試在哪。**找不到測試 = 不通過。**
