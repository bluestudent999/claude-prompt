# 開獎、RTP 與營運參數

> RTP（Return To Player）＝ 玩家長期平均能拿回多少。設 96% 就是「長期而言每投入 100 塊平均回 96 塊」。
> 這份管的是**開獎公不公正、數值查不查得到**。
> 目標值、權重表、注入比例這些**數字由營運訂**，不在這裡寫死（`business-logic.md` §5）。

---

## 1. 開獎的三條硬規則

1. **隨機來源必須是密碼學等級的**（`SecureRandom` 之類），不得用一般偽隨機。
   > 一般偽隨機的序列可被反推，而這關係到玩家的錢。不是效能問題，是正確性問題。
2. **開獎必須完整留痕且可回放**（不變量 I7）：隨機來源狀態、結果矩陣、命中的線、每線倍數、派彩金額、餘額前後值。
   > 判準：**任何一局事後都要能完整重演一次。** 玩家客訴「我明明中了」時，這是唯一的舉證方式。
3. **所有可調數值一律走設定，不得硬編**，且變更要留下版本紀錄。

---

## 2. 哪些是「營運可調參數」

`business-logic.md` §5 已經切分過：**從截圖看不出來的，本來就不是要複製的東西。**

| 屬營運參數 | 說明 |
|---|---|
| 符號權重表 | 決定各符號出現頻率 |
| RTP 目標值、是否含彩池 | 統計口徑由營運訂 |
| 彩池注入比例、三層分配、種子金額、歸零值 | `spec.md` §1.4.4 |
| PARTY 觸發機率、檔位權重 | 同上 |
| 徽章出現率 | 同上 |

**開發端的責任只有一個：確保它們可設定、改了有紀錄、改了有提示。**
（`spec.md` `AC-9.1`、`AC-10.12`、`AC-10.27`；對應任務 T-22）

> 這正是 brief §2.2 V-2「數值自主」要的東西。硬去猜參考站的數字，既做不到也沒有意義。

## 3. 模擬驗證（M-4，對應 T-23）

| 項目 | 要求 |
|---|---|
| 局數 | 100 萬局 |
| 允許誤差 | 設定值 ±0.5% 以內 |
| 前提 | 判定引擎要能脫離資料庫與 Spring 單獨執行（`architecture.md` §4） |

**報告至少要說清楚**：權重表版本、RTP 的統計口徑（含不含彩池）、實際回報率、各符號實際出現頻率與設定值的落差。

> **不得只寫「RTP = 96.2%」而不說口徑。** 彩池算不算進去差很多，那個數字單獨看沒有意義。

---

## 4. 偏差過大時的紀律（這條最重要）

> **先懷疑派彩實作，不要先調權重表。**

把權重調到「看起來對」會**同時蓋掉派彩的 bug** —— 而且因為 RTP 達標了，之後沒有人會再去查。
那個 bug 上線後會變成真實的資金差異。

正確順序：

1. 跑 `/payout-verify`，確認實測回歸（T-09）仍然通過。
2. 檢查各符號實際出現頻率與設定權重的落差 —— 落差大代表 RNG 或權重套用有問題，不是賠率問題。
3. 上面兩項都乾淨，才考慮調權重。

---

## 5. 彩池的工程要求

**業務規則看 `spec.md`**（觸發、檔位、瓜分、歸零都在 §1.4.3 與 §1.4.4）。這裡只有兩條工程要求：

- **守恆可對帳**（不變量 I6）：`累計注入 − 累計派出 = 當前餘額`，任何時刻成立。
- **瓜分是併發結算**（T-16）：多人同時中獎的路徑必須有刻意構造的併發測試，單執行緒測不出來。
