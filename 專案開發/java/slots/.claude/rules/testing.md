# 測試政策

> 這個專案的測試有一個特別任務：**證明我們複製得準。**
> 一般測試問「程式有沒有 bug」；這裡還要問「跟參考站一不一樣」。
> 技術棧：JUnit 5 + Mockito；需要資料庫的整合測試用 Testcontainers，**禁止連真實開發／生產資料庫**。

---

## 1. 風險層級（決定要寫多少測試）

| 層級 | 什麼算這一級 | 要求 |
|---|---|---|
| **L1（高）** | 判定引擎、派彩計算、扣款派彩、冪等、彩池累積與結算 | **強制**。單元測試 + 整合測試都要 |
| **L2（中）** | 一般 Service、API 入口、記錄查詢、WebSocket 推送、前端行為 | 建議覆蓋，優先單元測試 |
| **L3（低）** | 設定檔、DTO、文案、純重構 | 不強制，過編譯與 Code Review 即可 |

> **只要動到錢，就是 L1。** 沒有「這個改動很小所以不用測」這種例外 —— `spec.md` §1.1.3 的 M-5 目標是派彩錯誤 **0 件**。

## 2. 三種保真度測試

### 2.1 規則對拍（M-1）

每一條玩法規則要有一個測試，**測試上標出它對應的 spec 編號**：

```java
// spec.md §1.4 R-3（WILD 替代，按被替代符號計價）
```

這不是註解潔癖 —— 沒有編號的規則測試，代表沒人知道它的依據，日後也沒人敢改。

**只有「取樣驗證」類的規則算進 M-1**。我方自訂（spec 標 `🔧`）與營運參數不算，它們本來就沒有對照組（`rules/fidelity.md` §3）。

### 2.2 實測案例回歸（M-2，對應 T-09、`AC-3.9`）

用參考站**實際跑出來、有截圖佐證**的盤面當測資，輸出必須完全相同。
測資本體在 `plan/reference-sampling.md`，不要抄進測試註解，標節號即可。

> **T-09 是全案的收斂點**（`backlog.md` 建議實作順序第 5 批）：它一次驗證線型、賠率、替代規則、派彩公式。
> **T-09 沒過，後面所有派彩相關任務都不該開始。**

### 2.3 畫面行為對拍（M-3，對應 `AC-8.x`）

對照截圖逐項檢查。目前沒有自動化手段，用檢查表人工過。

## 3. 一定要刻意構造的四種情境

| 情境 | 為什麼危險 | 測什麼 |
|---|---|---|
| **重複請求** | 玩家連點、網路重送 | 同一局重複進來，錢只動一次（I4、`AC-4.6`） |
| **中途中斷** | 動畫播到一半關瀏覽器 | 派彩仍入帳且只入一次（I3、`AC-4.7`） |
| **併發** | 多人同時中 GREAT PARTY（T-16） | 瓜分結果正確，且彩池對帳等式仍成立（I6） |
| **跨進出的狀態** | 免費旋轉序列、BONUS 選箱中途離開（T-27、T-32） | 狀態完整還原（`AC-10.11`、`AC-10.25`） |

> 這四種在單執行緒、手動點一點的測試裡**永遠測不出來**。

---

## 4. RTP 模擬（M-4，對應 T-23）

100 萬局、誤差 ±0.5% 以內。**不放進一般 CI**（跑太久），獨立跑並留下報告。細節見 `rules/rng-rtp.md` §3。

---

## 5. 提交前的測試閘門

1. `./mvnw test` 全綠（含整合測試）。
2. 動到 L1 範圍 → 對應的對拍測試與實測回歸必須存在且通過。
3. 動到權重表或派彩 → 跑一次 RTP 模擬，報告附在 MR。
4. **既有測試不得有任何一個變紅。** 改測試讓它變綠之前，先證明是測試寫錯，不是程式寫錯。
5. 改過 spec 的話，新增／變動的 AC 要有對應測試（`rules/plan-authority.md` §2）。
