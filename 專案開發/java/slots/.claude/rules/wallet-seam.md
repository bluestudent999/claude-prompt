# 三個接縫（v1 只定契約，不接外部系統）

> 「接縫」= 現在把介面切好，**未來要換掉時不必動遊戲核心**。
> 企劃列了三個：錢包（SE-1）、啟動與身分（SE-2）、獎勵事件（SE-3）。
> 範圍與決議看 `plan/yummy/brief.md` §4，這份只寫工程要求。

---

## SE-1 ｜ 錢包

沿用平台既有錢包，**不自建餘額**（不變量 I2）。v1 以試玩實作填充。

### 介面至少要有

查餘額（顯示用）／扣款（下注前）／派彩（開獎後）。

### 硬規則

- **每次扣款與派彩都要帶本局唯一的識別碼**，讓錢包端能擋掉重複請求（I4）。**重試必須用同一個碼**，不得每次重新產生。
- **查餘額的結果不得當作扣款依據** —— 查完到扣款之間餘額可能已變。扣款本身要能拒絕。
- **扣款成功但後續失敗** → 必須有明確的補償路徑（`spec.md` E-2、E-3；任務 T-12）。不得靜默留下「錢扣了、局沒開」。
- 試玩實作**不得**與真實錢包共用設定或連線資訊，避免誤接（I8）。

> 串接方式屬 `➡️ OQ-15 defer-to-dev`，**開發端自己決定**，決定後寫進技術設計並回填 backlog（`plan-authority.md` §5）。

### 切換真金流時要補

儲值／提現、支付渠道、實名認證、交易對帳、法遵與稽核報表。**法遵通常有前置期，不是上線前一週能補的。**

## SE-2 ｜ 從大廳啟動、認出玩家是誰

大廳用 `?Code=YUMMY_001&Typ=BIGO_YUMMY` 開啟遊戲。憑證傳遞方式屬 `➡️ OQ-12 defer-to-dev`，**開發端自決**。

### 硬規則

**不得把玩家身分交由前端自稱。** 前端可以帶憑證，但「這是誰」必須由後端驗證後決定（I1 的延伸）。

## SE-3 ｜ 獎勵事件（泛化，不得硬編）

記錄模組要能承載**不只一種**獎勵事件類型，新增一種不需要改既有資料結構（`spec.md` R-15；任務 T-20）。

### 為什麼

參考站的記錄頁有一個獨立分頁叫「幸運禮包記錄」，兩次取樣都是空的，**沒有人知道它是什麼**。
v1 空實作，但型別欄位要留著。

> 這是**已知的未知**：知道有東西、不知道是什麼。
> 硬編成「獎勵 = 免費旋轉」，等哪天搞清楚了，要回頭改的是**派彩與記錄的資料結構**，不是加一個 if。

### 但也不要過度

留一個型別欄位與可擴充的記錄結構就夠了，**不需要外掛框架或插件機制**。
