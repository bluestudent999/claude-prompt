# 企劃書的修改權限與回寫紀律

> **這份範本的前提：企劃階段已經跑完，而且你有權改所有企劃文件。**
> `plan/` 下的東西是**活的工作文件**，不是別人丟過來、你只能照做的規格書。
> 進入開發後**不需要再切回企劃範本**，該改的自己改。

---

## 1. 你可以改哪些

| 文件 | 內容 | 你的權限 |
|---|---|---|
| `plan/yummy/backlog.md` | 32 顆 T 任務、DAG、依賴、AC 對應 | ✅ 可改：拆任務、調順序、補依賴、回填狀態 |
| `plan/yummy/spec.md` | 業務規則 R-*、邊界 E-*、驗收條件 AC-* | ✅ 可改：補規則、修錯、新增 AC |
| `plan/yummy/business-logic.md` | 角色、資料流、Flow-A~G、關鍵規則 | ✅ 可改 |
| `plan/yummy/brief.md` | 範圍、成功指標 | ✅ 可改（範圍變動要顯眼標記，見 §3） |
| `plan/reference-sampling.md` | 參考站取樣紀錄（事實依據） | ✅ 可改，但**只能新增取樣或更正錯誤**，見 §4 |
| `plan/Yummy_Slot_Development_Plan.md` | 最早的企劃書，多處已被後續文件取代 | ✅ 可改（或直接標為已過時） |

**沒有「這要回企劃決」這回事。** 發現規格寫錯、漏了情境、任務切得不對 —— 直接改，然後照 §2 留痕。

---

## 2. 改了就要回寫（唯一的硬規則）

改動可以自己決定，但**不能只存在對話裡或只存在程式碼裡**。

| 你改了什麼 | 至少要同步 |
|---|---|
| 業務規則 | `spec.md` §1.4 對應的 R 編號 |
| 新的邊界情境 | `spec.md` §1.5 的 E 編號 + 至少一條 AC |
| 驗收條件 | `spec.md` §1.6 的 AC 編號 + `backlog.md` 的「對應 AC」欄 |
| 任務範圍或依賴 | `backlog.md` 的任務列與 DAG |
| 範圍進出（In／Out Scope） | `brief.md` §4 |
| 新取樣到的參考站事實 | `reference-sampling.md` 的 §S 節 |

**判準**：一個新來的人只讀 `plan/`，能不能完整知道現在的規則是什麼？不能 → 你還沒回寫完。

### 保留原文，不要直接覆蓋

改規則時**保留原本那條**，在旁邊註明改成什麼、為什麼改、日期。
理由：這個專案的核心是「複製得準」，日後要追「當初為什麼跟參考站不一樣」，沒有原文就追不回來。

---

## 3. 三種改動要特別標記

不是要你停下來問，是要讓改動**看得見**：

| 改動 | 標記方式 |
|---|---|
| **範圍變動**（把 Out of Scope 拉進來、或把 In Scope 砍掉） | 在 `brief.md` §4 該列標 `⚠️ 變更 <日期>：<原因>` |
| **與參考站不一致的決定**（我方刻意不照抄） | 在 `spec.md` 該條規則標 `🔧 自訂：<原因>`，並在 M-1 對拍表排除該條 |
| **影響已完成任務的規則變動** | 在 `backlog.md` 把受影響的 T 任務標回未完成，說明要重做什麼 |

第三種最容易漏。改了 R-7，但 T-11、T-12 已經做完了 —— 那兩顆要標回去重驗，不是當作沒事。

---

## 4. `reference-sampling.md` 的特別規則

這份是**參考站的事實紀錄**，不是我們的設計文件。它跟其他文件的差別在於：

- ✅ **可以新增**：又取樣到新畫面、新規則、新測資 → 加新的 §S 節。
- ✅ **可以更正**：發現先前判讀錯了 → 更正，並註明是根據哪張截圖更正的。
- ⚠️ **不可以寫入我方的決定**。我們自己訂的數值與規則寫在 `spec.md`，不要混進取樣紀錄。

> 混進去的後果：日後分不清「這是參考站真的這樣」還是「這是我們當初決定的」，
> 而 M-1 保真度對拍正是靠這個區分。

### 三級事實標記照樣用

取樣紀錄用 `無標記`（截圖可見或已實測）／`【推測】`（未證實）／`【缺】`（未取樣）區分確定程度。

**這不是禁令，是資訊。** 實作時照樣可以動：

- 依據是**無標記** → 照做。
- 依據是 `【推測】` 或 `【缺】` → 你可以自己決定怎麼做，但**要在 `spec.md` 寫下你決定了什麼**，並在該條標明依據等級。

這樣日後有人回頭查，看得出「這條是驗證過的」還是「這條是我們當初自己定的」。
