# 開發流程

> **前提：企劃已經跑完。** `plan/yummy/` 有 spec（87 條 AC）、backlog（32 顆任務、DAG、AC 全覆蓋）、business-logic。
> 工單來源就是 `backlog.md`。**進開發後不需要再切回企劃範本** —— 企劃文件你有權直接改（`rules/plan-authority.md`）。

---

## Step 0 ｜ 取任務

從 `plan/yummy/backlog.md` 取一顆 T 任務。它已經幫你標好四件事：

| 欄位 | 用途 |
|---|---|
| `Required Spec Sections` | **只讀這幾節**，不要通讀 35KB 的 spec —— 這是上下文預算的核心 |
| `Scope 邊界` | 這顆做什麼、不做什麼 |
| `Depends On` | 前置任務未完成就不要開始 |
| `對應 AC` | 做完要驗收哪幾條 |

backlog 的「建議實作順序」已經拓撲排序成 9 批，同批可平行。兩個關鍵節點：

- **T-09（引擎回歸驗證）** 是收斂點。沒過，後面派彩相關任務都不該開始。
- **T-11（派彩入帳）** 是最大扇出點，後接 7 顆。R-7 鐵則做錯，彩池／批量／BONUS／免費旋轉全部受影響。

> 覺得任務切得不對、依賴漏了、AC 有問題？**直接改 backlog 與 spec**，照 `plan-authority.md` §2 回寫。

---

## Step 1 ｜ planner 拆解

產出 `plan/task-<任務編號>-plan.md`，至少要有：

1. **這次要做什麼**（一句話，玩家看得到的說法）
2. **依據**：spec 的 R／E／AC 編號（照 backlog 的 `Required Spec Sections`）
3. **碰到哪幾條工程不變量**（`game-invariants.md` I1~I8），每條配一個驗收測試
4. **要不要動企劃文件**：發現規格有洞就在這裡說明要怎麼補
5. **驗收清單**：做完逐項打勾

---

## Step 2 ｜ 實作

- 一顆任務只做一件事。動到 A 的提交裡不得順手改 B。
- 每一條玩法規則的實作旁，**標出 spec 編號**（`fidelity.md` §2）。
- 規則內容**不得**抄進 `.claude/` 或程式註解 —— 只標編號。

### 規格不夠用的時候

spec 沒寫到、寫錯、或與實作衝突 → **自己補、自己改**，然後回寫（`plan-authority.md`）。
不要在程式裡默默做一個決定卻不寫進 spec —— 那個決定下次沒人找得到。

---

## Step 3 ｜ 測試

依 `rules/testing.md`：L1 強制、對拍測試標 spec 編號、四種危險情境（重複請求／中途中斷／併發／跨進出狀態）要刻意構造。

---

## Step 4 ｜ Review（依改動內容派工，可平行）

| 動到什麼 | 派給誰 |
|---|---|
| 玩法規則的實作 | `fidelity-reviewer` |
| 派彩、金額、扣款時序、冪等 | `payout-guard` |
| RNG、權重、彩池、模擬 | `rng-rtp-reviewer` |
| package 結構、模組邊界、前後端職責 | `arch-guard` |
| 前端 | `game-client-reviewer` |
| 其他 Java 程式碼 | `code-reviewer` |

---

## Step 5 ｜ 提交與回填

1. `./mvnw test` 全綠。
2. 回填 `backlog.md` 的任務狀態。
3. 有改過 spec／brief／business-logic → 確認已回寫且編號一致。
4. **沒回填 = 任務未完成。**

---

## Reviewer 的輸出格式（Harness Output Contract）

所有 reviewer 的最後一段必須是這五個欄位：

| 欄位 | 內容 |
|---|---|
| `Status` | `approve` / `warning` / `block` |
| `Summary` | 一句話結論 |
| `Counts` | 各嚴重度計數，如 `HIGH 2 / MED 1 / LOW 3` |
| `Next actions` | 具體要做什麼，一條一行 |
| `Artifacts` | 每筆 `檔案:行號 — 問題 \| fix: 具體改法` |

**空話禁令**：不要寫「建議優化結構」「可考慮重構」。要寫「把 X 從 A 改成 B」。給不出具體改法就不要提。

### 派子 Agent 時的 briefing

子 Agent **不繼承對話上下文**。派工必須自包含：plan 路徑 + diff 片段 + 相關規範條文 + 提醒輸出 Harness Output Contract。**Briefing ≤ 500 字。**

## OQ 與「要問使用者」的兩條硬規則

### 一、用國中生聽得懂的話寫

每一則 `⏳` OQ、以及每一個你要丟給使用者的問題，都必須讓**一個國中生讀完就能直接回你 A 或 B**。
做不到就是寫壞了，**重寫**，不要送出去。

**每則必含三段：**

| 段 | 寫什麼 |
|---|---|
| **情況** | 什麼時候、什麼狀況下會遇到這件事 |
| **卡住什麼** | 不決定的話，哪個功能／流程做不下去 |
| **選項** | 每個一句話 + 它的代價；傾向的那個後面標「（建議：一句理由）」 |

**禁止：**

| ❌ | 為什麼不行 |
|---|---|
| 只寫「OQ-5 未決，無法繼續」 | 看的人不知道 OQ-5 是什麼 |
| 用內部代號當問題本體（任務編號、章節號、模組名、函式庫名） | 那是我們的編號，不是問題 |
| 用技術名詞而不解釋（冪等、併發、接縫、契約、回歸） | 要用就當場用一句話說明白 |
| 沒有選項，只寫「請指示」 | 沒選項等於要對方從零想，那是我們的工作 |

> **反例**：「彩池瓜分的比例演算法與時間窗未定義」
> **正例**：「大獎被好幾個人同時中時，錢怎麼分？」＋ 情況 ／ 卡住什麼 ／ A、B、C 各自的代價

### 二、沒問題就不要硬生問題

送出之前先自問：**這題我能不能從需求、既有文件、或本範本的既有慣例，推出一個合理的預設？**

- **能** → **直接採用預設**，在產出裡用一句話寫明「我採了什麼、為什麼」，然後繼續做。**不要開 OQ。**
- **不能，而且不同答案會導向實質不同的工作** → 這才是真的 OQ，照第一條的格式寫。

> **為什麼**：問題本身有成本。把自己判斷得出來的事丟回去，等於把工作推回給對方；
> 而且會**稀釋真正需要拍板的那一題** —— 一次丟五個問題，重要的那個就被淹掉了。
> **湊數的 OQ 比沒有 OQ 更糟。**

> 兩條不衝突：第二條決定**要不要問**，第一條決定**問了怎麼寫**。

### 本專案的 OQ 現況

`backlog.md` 文末只剩兩則 `➡️ defer-to-dev`（OQ-12 憑證傳遞、OQ-15 錢包串接），
