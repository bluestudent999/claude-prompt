# 核心不變量 I1 ~ I10（最高紅線）

> **這 10 條是本系統正確性的定義。** 來源：開發企劃書 §4。
> **每一條都必須有對應的自動化測試**；Code Review 以此為檢查清單；違反即 `block`，沒有例外。

## 三條需要特別小心的

### I6 是最容易寫錯的一條

補塊 API 的存在意義就是**重掃**。如果重掃會重複發事件，這個維運工具反而會製造**資損**。

實作靠 `INSERT ... ON CONFLICT DO NOTHING` 搭配冪等鍵達成。

> **Review 檢查點：** 任何新增的寫入路徑都要問「這條路徑被執行兩次會怎樣」。答不出來就是還沒想清楚。

### I8 是多租戶新增中最關鍵的一條

- 它是**正確性**問題，不是功能問題 —— 違反即**租戶資料洩漏**，可能構成法遵事故。
- **在單租戶測試環境下 100% 測不出來**。少了 `WHERE tenant_id = ?`、拉取 API 忘記過濾、歸屬解析寫錯 —— 只有一個租戶時全部「正常」。
- 必須在 **P1 就有測試**，且依 `testing.md` 以兩租戶為所有整合測試的基準環境。

### I9 由資料庫約束強制

成本趨近於零，但它是整個路由模型的地基。`watched_addresses` 的 `uk_watched_addr UNIQUE (chain, address)` 就是它 —— **不要為了「同一地址讓兩個租戶共用」這種需求去拿掉這個約束**，那會讓歸屬解析變成不確定。要改先回報。

## ⚠ I7 與 D17 的文件內部矛盾（實作前必須確認）

開發企劃書的 I7 描述提到：

> 「…並驗證 receipt 回傳 `null` 時正確轉為 **`reorged`**」

但同一份文件的 **D17** 與 bigpicture 的**取代對照表**明確寫著：

- D17：只掃已確認區塊 `head - N`，**取消 Reorg 回溯與確認數狀態機**
- 取代對照表：`payment.reorged` **已自契約移除**，下游不需實作沖銷邏輯
- 取代對照表：狀態機簡化為 `detected`（選用）→ `confirmed`，**`pending` 與 `reorged` 都不存在**

**這是不變量表未完全跟上 D17 的殘留。**

**處置（硬規則）：**

1. **以 D17 與取代對照表為準** —— 不實作 `reorged` 事件型別、不實作 Reorg 回溯狀態機。
2. I7 的**有效部分**是：事件僅在達到該租戶安全確認數時發出，且發出前重查 `eth_getTransactionReceipt` 確認非 `null` 且 `blockNumber` 與 DB 一致。
3. Receipt 重查回傳 `null` 或 `blockNumber` 不符時 → **不發出事件並告警**，而不是「轉為 reorged」。
4. **實作到 S12 / S19 / S23 前，把這個矛盾列為 OQ 請使用者確認**，並在確認後**回頭修正開發企劃書的 I7 文字**，不要讓下一個 session 再撞一次。

## 使用方式

- **planner**：每個步驟的 plan 必須在 §0 標出「涉及哪些不變量」，並在驗收計畫中寫出對應測試。
- **實作者**：改動前先查上表「由哪些步驟保證」，確認自己是否踩在某條不變量上。
- **invariant-guard**：以本表逐條檢查，並驗證對應測試**確實存在且通過**（不是「應該有」）。
- **新增不變量**：若實作中發現需要第 11 條，**回報使用者**並更新開發企劃書 §4 —— 不變量清單是規格，不是註解。
