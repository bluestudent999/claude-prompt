# 測試政策

> 來源：開發企劃書 §8、實作步驟企劃書 §1.2 ~ §1.3。
> **本專案的測試不是覆蓋率遊戲**——它是 10 條不變量的驗證機制。

---

## 1. 兩租戶基準環境（硬規則，最重要的一條）

> **所有整合測試一律建立兩個租戶** `tenant-a`、`tenant-b`，各含**專屬收款地址**與**各自的訂閱者**。

**理由：** 租戶隔離的 bug 有一個共同特徵 —— **在單租戶環境下 100% 測不出來**。

少了 `WHERE tenant_id = ?`、拉取 API 忘記過濾、歸屬解析寫錯關聯 —— 這些在只有一個租戶時**全部「正常」**，一旦第二個租戶上線就變成**資料洩漏**。

**因此不是「另外加幾個租戶隔離測試案例」，而是把兩租戶設為所有測試的預設 fixture。** 每個既有測試案例都順帶驗證了隔離性，成本幾乎為零，覆蓋率遠高於另外寫幾個專門案例。

### 必測的越權情境（容易漏）

- 以 A 的憑證呼叫拉取 API，**帶入 B 的 `sequence` 值** → 必須取不到 B 的事件
- 以 A 的憑證呼叫 Admin API 補塊／操作 B 的交易 → 必須被拒絕
- 將**已屬於 A 的地址指派給 B** → 必須被資料庫約束拒絕（I9）
- 拉取回應的 `latest_sequence` → 必須是 A 視角的值，不得洩漏全域最大序號

> **Review 檢查點：** 看到一個新的查詢或 API，第一個問題永遠是「**它有沒有依訂閱者的租戶範圍過濾**」。

## 2. 測試分層與命名

| 層級 | 位置 | 用途 | 速度 | 進 CI |
|------|------|------|------|-------|
| 單元測試 | `src/test/java/**/*Test.java` | 純邏輯，無 I/O | 毫秒 | ✅ |
| **架構測試** | `src/test/java/**/ArchitectureTests.java` | Modulith `modules.verify()` + ArchUnit 分層規則 | 秒 | ✅ **S01 就要有** |
| 整合測試 | `src/test/java/**/*IT.java` | 對真實 PostgreSQL（**Testcontainers**）與 **Mock RPC** | 秒 | ✅ |
| 端到端 | `src/test/java/**/*E2ETest.java` | 對測試網真實 RPC | 分鐘 | ❌ 不進預設流程 |

> **Domain 層的單元測試不需要 Spring context**——它是純 Java（`architecture.md` §1）。看到 Domain 測試掛 `@SpringBootTest`，那是分層破了的訊號。

### B 軌（維運後台）的驗收依據不同

| | A 軌（S 步驟） | B 軌（T 任務） |
|---|---|---|
| 驗收依據 | 步驟列出的驗收測試 | **對映的 AC 編號**（`spec.md` §1.6） |
| 正確性軸線 | 10 條不變量 | **R# 業務規則 + E# 邊界情境** |

**B 軌必須測的三類**（其餘依 AC）：
1. **租戶範圍過濾**（R2）—— 比照兩租戶原則：以 Operator A 的身分呼叫，**必須取不到 B 的租戶**（清單、下拉、查詢結果、地址反查皆然）
2. **三種狀態可區分**（E1／E10）—— 服務端逾時 → **不得渲染成空清單**；確實沒資料 → 空狀態文案
3. **憑證不落地**（R9／R10）—— 明文不進 storage／網址／log／狀態管理，重新整理後取不到

> **B 軌的兩租戶原則同樣適用**：後台的租戶隔離 bug 一樣在單租戶環境下 100% 測不出來。

**命名規範：** `should_<預期行為>_when_<條件>`

```java
should_reject_when_address_belongs_to_another_tenant
should_return_empty_when_cursor_points_to_other_tenant_sequence
should_not_duplicate_events_when_range_is_rescanned
```

## 3. Mock RPC 是基礎設施，不是「有空再做」

**Reorg、Failover、逾時、429、資料格式異常在真實測試網上無法按需觸發。** 這是很多團隊上線後才發現的問題。

- **必須在 P1（S05）就建好**，列為正式交付項。
- 需能**依腳本回放**：先給 A 鏈、再改口給 B 鏈的分叉情境；主 provider 斷線；429 限流；回傳格式異常。
- 它是 I7 與 Failover 邏輯**唯一可靠的驗證手段**，也是整個測試策略的地基。

> 詳細情境腳本見 `/mock-rpc` skill。

## 4. 各不變量的驗證方式

| 不變量 | 測試手法 |
|--------|---------|
| I1 | 事務中途**注入例外**，驗證 DB 無任何殘留 |
| I2 | 掃 10,000 塊持續抽樣，驗證無下降、無跳號 |
| I3 | **同時啟動 3 個同鏈實例**，驗證只有 1 個取得 Advisory Lock |
| I4 / I5 | DB UNIQUE 約束 + 重掃測試 |
| I6 | **同一區間連續重掃 3 次**，驗證資料列數與事件數不變 |
| I7 | Mock RPC 重播腳本；驗證兩個門檻不同的租戶各自在正確深度晉升 |
| I8 | 兩租戶交叉注入，驗證事件流完全不交叉 + 越權嘗試被拒 |
| I9 | DB 約束；驗證指派給第二個租戶被拒絕 |
| I10 | B 補齊 15,000 筆時，量測 A 的 P95 拉取延遲 |

## 5. 單元測試的 fixture 用**真實主網交易**

ABI 解碼、地址正規化、Base58 ↔ Hex 轉換、金額精度換算這幾類，**不要自己編造測試資料**。

從區塊瀏覽器抓幾筆真實的 USDT 轉帳原始 Log 當 fixture，比對解析結果。理由：自己編的資料會不小心編成「自己的實作剛好會過」的樣子。

- **TRON 地址轉換**：以 **100 組真實地址**驗證（S22 驗收標準）。
- **契約測試**：與下游共用一份 JSON Schema，雙方 CI 各自驗證。

## 6. Definition of Done（每個步驟都適用）

一個步驟算完成，必須**全部**滿足：

1. 該步驟列出的**驗收測試全部通過**
2. 既有測試**沒有任何一個變紅**（迴歸）
3. 靜態檢查通過（Checkstyle／SpotBugs）
4. 涉及不變量的步驟，**該不變量的測試也通過**
5. **`ArchitectureTests` 通過**（`modules.verify()` + Domain 純度 + 依賴方向）；**B 軌另需對映 AC 全部有驗證**
6. 涉及 migration：**版本號驗證器通過**（`flyway-migration.md` §7；S02 交付項）
7. **實作步驟企劃書已回填完成紀錄**

> 第 2 條是最常被忽略的。改了共用邏輯後只跑「自己這個步驟的測試」是不夠的。

---

## 7. 不要做的事

| ❌ | 為什麼 |
|---|--------|
| 為了衝覆蓋率寫無斷言的測試 | 本專案的測試存在意義是驗證不變量，不是數字 |
| 整合測試連真實 RPC | 慢、不穩定、無法觸發異常情境。用 Mock RPC |
| 單租戶 fixture | 見 §1 —— 隔離 bug 在單租戶下測不出來 |
| 把 `*E2ETest.java` 放進 CI 預設流程 | 需要測試網與真實資金，會讓 CI 隨機失敗 |
| 「這個改動很小，不用跑整合測試」 | 改到共用查詢時，最小的改動就是 I8 破口 |
| 為尚未實作的能力先寫測試骨架 | 範圍紀律；且會讓 CI 長期有紅燈或被 `@Disabled` 淹沒 |
