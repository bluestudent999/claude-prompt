> 本專案由 `plan/2026-08-17-crypto-node-implementation-steps.md` 的 **S01 ~ S38** 推進。

**OQ 硬規則：**
- 可用 grep / Read / 跑測試驗證的 → **planner 自答鎖定**，不丟給使用者。
- 需要判斷的 → **必列 OQ，嚴禁推測**。本專案典型必問：
  - **模組切分定案**（`architecture.md` §3 只是提議）—— S01 實作前必問
  - **I7 與 D17 的矛盾**（`invariants.md` 末段）該怎麼對齊

  - 原生幣入金是否要支援（D8，影響 40% 工作量）
  - 任何需要下游配合的契約調整
- **OQ 未解答前禁止編寫業務代碼**；決議必回寫 plan（原文加刪除線 + ✅ 決議），只存 chat 不算數。

## Step 2：實作

**Golden Rule：依計畫實作。** 禁止自行重設計、優化架構、或新增未經計畫的需求。唯一真理來源是 `plan/`。

- **最小化讀取**：只讀該步驟需要的檔案，不讀全專案。
- **禁止越權決策**：不自行新增事件型別、資料表欄位、對外 API、設定項。
- **禁止順便重構**：不修改與本步驟無關的檔案。
- **Stop Rule**：遇到文件互相矛盾（bigpicture vs 開發企劃書、I7 vs D17）→ **立即停止並回報**，不要挑一個猜。

**每次寫入路徑都要問：** 「這條路徑被執行兩次會怎樣？」（I6 冪等）
**每次新增查詢都要問：** 「它有沒有依租戶範圍過濾？」（I8 隔離）
**每次新增類別都要問：** 「它屬於哪一層？依賴方向對嗎？」（`architecture.md` §1）
**想用 `@ApplicationModuleListener` 時要問：** 「這件事在 I1 的四項寫入範圍內嗎？」是 → **不能用**（`architecture.md` §4）

## 步驟不通過時

實作步驟企劃書 §0.3 有規範。原則：

- **不要為了讓測試過而放寬驗收標準。** 驗收標準是規格。
- 若判定該步驟的驗收標準本身有問題 → 列 OQ 回報，由使用者裁決是否修改企劃書。

## OQ 與「要問使用者」的兩條硬規則

### 一、用國中生聽得懂的話寫

每一則 `⏳` OQ、以及每一個你要丟給使用者的問題，都必須讓**一個國中生讀完就能直接回你 A 或 B**。
做不到就是寫壞了，**重寫**，不要送出去。

**每則必含三段：**

| 段 | 寫什麼 |
|---|---|
| **情況** | 什麼時候、什麼狀況下會遇到這件事 |
| **卡住什麼** | 不決定的話，哪個功能／流程做不下去 |
| **選項** | 每個一句話 + 它的代價；傾向的那個後面標「（建議：一句理由）」 |

**禁止：**

| ❌ | 為什麼不行 |
|---|---|
| 只寫「OQ-5 未決，無法繼續」 | 看的人不知道 OQ-5 是什麼 |
| 用內部代號當問題本體（任務編號、章節號、模組名、函式庫名） | 那是我們的編號，不是問題 |
| 用技術名詞而不解釋（冪等、併發、接縫、契約、回歸） | 要用就當場用一句話說明白 |
| 沒有選項，只寫「請指示」 | 沒選項等於要對方從零想，那是我們的工作 |

> **反例**：「彩池瓜分的比例演算法與時間窗未定義」
> **正例**：「大獎被好幾個人同時中時，錢怎麼分？」＋ 情況 ／ 卡住什麼 ／ A、B、C 各自的代價

### 二、沒問題就不要硬生問題

送出之前先自問：**這題我能不能從需求、既有文件、或本範本的既有慣例，推出一個合理的預設？**

- **能** → **直接採用預設**，在產出裡用一句話寫明「我採了什麼、為什麼」，然後繼續做。**不要開 OQ。**
- **不能，而且不同答案會導向實質不同的工作** → 這才是真的 OQ，照第一條的格式寫。

> **為什麼**：問題本身有成本。把自己判斷得出來的事丟回去，等於把工作推回給對方；
> 而且會**稀釋真正需要拍板的那一題** —— 一次丟五個問題，重要的那個就被淹掉了。
> **湊數的 OQ 比沒有 OQ 更糟。**

> 兩條不衝突：第二條決定**要不要問**，第一條決定**問了怎麼寫**。
