# 後台串接規範（crypto-node-web ↔ crypto-node）

> **適用對象：** `crypto-node-web` 維運後台。規格來源：`plan/crypto-node-web/{brief,spec,backlog}.md`。
> 本文管**兩層串接**與**跨服務契約**；UI 呈現規則見 [`web-frontend.md`](./web-frontend.md)。

---

## 1. 拓樸與連接方式（已決，2026-08-26）

**連接方式：後台後端以「內網 RESTful」呼叫 crypto-node 的 Admin API。**

```
[瀏覽器]
   │ ① 前端 ↔ 後台後端（自訂契約）
   ▼
[nginx]  ← ⚠ 內網／VPN 邊界的唯一執行點（§2）
   │
   ▼
[crypto-node-web]        ← 同 repo 模組；自有資料只有四類（R11）
   │ ② 內網 RESTful → /admin/**
   ▼
[crypto-node-service]    ← 業務資料的唯一真實來源
```

**Repo 結構（已決）** —— 三個模組平行：

```
crypto-node/
├── crypto-node-flyway/     DB migration
├── crypto-node-service/    A 軌：鏈下索引與事件中繼
└── crypto-node-web/        B 軌：維運後台（前端 + 後台後端）
```

| 層 | 契約 | 誰擁有 |
|---|------|--------|
| ① 前端 ↔ 後台後端 | 本專案自訂，可自由演進 | 我們 |
| ② 後台後端 ↔ crypto-node | **既有的 Admin API**（`event-contract.md` §4） | crypto-node 服務端 |

> **後台是 Admin API 的新消費者，不是它的擁有者。** 需要 Admin API 新增能力 → 那是**服務端變更**，走 A 軌流程，不是在後台這邊繞過去。
> 同 repo 的好處：契約與消費端可在**同一個 commit / MR** 一起改（見 `git-workflow.md`）。

### ⚠ 這個選擇確認了 R13a 的風險成立

企劃在 OQ-9 已明確警告：

> 「後台若以**代為呼叫**方式接在服務前面，服務端『只有內網能操作』的保護會**靜默失效**。」

**「內網 RESTful」就是代為呼叫。** 因此：

- `crypto-node-web` 本身就在內網 → 服務端的網段過濾**對後台這條路徑永遠放行**
- **後台後端的授權判定不是「多一道防線」，它是唯一的那道**
- §2 的 nginx 三項從「建議」升級為**必須**

**不要因為「反正都在內網」而放鬆任何一項。**

## 2. ⚠ 最高紅線：內網邊界會靜默失效（R13a）

**crypto-node 服務端的「只允許內網網段呼叫 `/admin/**`」是依連線來源位址判斷、且完全忽略代理標頭。**

決議 3 之後 crypto-node 以 nginx 搭配域名對外、後台呼叫域名 —— 於是：

```
維運人員 → nginx → crypto-node
                ↑
        服務端看到的來源是 nginx 自己（落在內網網段）
        → 網段過濾對所有請求一律放行 → 保護等於不存在
```

**這是靜默失效：不會報錯、不會有 log、測試也不會紅。**

### 硬規則（三項缺一不可）

1. **nginx 必須只允許內網／VPN 來源存取 `/admin/**`**。
2. **不得存在繞過 nginx 直達服務的路徑** —— 有一條就等於邊界不存在。
3. **服務端的網段過濾在此架構下不可再計入防線** —— 必須明文記錄在部署文件裡。

> **為什麼第 3 條要明文寫：** 不寫的話，會有人以為「還有兩道防線」而各自放鬆一點，最後一道都不剩。

### 對開發的直接要求

- **後台後端不得成為 Admin API 的公開代理。** 任何「把請求原樣轉發給 crypto-node」的端點都是把 Admin API 開到後台的存取範圍上。
- 後台後端呼叫 Admin API 時**必須自行完成授權判定**（權限級別 + 租戶範圍），**不能依賴** crypto-node 那層擋。
- R13 的驗收**不在後台側**（後台驗不到 nginx 設定），由**部署驗收**承接。實作時要明確標出「這一條我驗不到」，不要假裝有測試覆蓋。

## 2.5 Admin API Client 的實作要求（內網 RESTful 的直接後果）

### 架構落點：走 Port，不要讓 Application 直接碰 HTTP

`crypto-node-web` 沿用 A 軌的六角分層紀律（`architecture.md` §1~§2）：

| 層 | 放什麼 |
|---|--------|
| **Domain**（零框架） | 權限級別判定、租戶範圍規則、操作紀錄的組成、危險操作的分類 |
| **Application** | 宣告 **`CryptoNodeAdminPort`**（要什麼能力），事務邊界 |
| **Infrastructure** | **REST Adapter 實作該 Port**，負責 HTTP、序列化、錯誤映射 |

**為什麼這裡必須有 Port**（對照 `coding-style.md` §8 的判準「隔離的是哪一個已知的變動源」）：
- Admin API 會隨 A 軌演進（三個跨系統依賴就是例子）
- 連接方式本身是 OQ-9 決議的產物，**未來可能改**
- 兩個都是**已知會變**的來源 → Port 是結構性設計，不是投機抽象

> **裁剪：`crypto-node-web` 不需要 Modulith 模組切分。** 它是 19 顆 TASK 的後台，模組切分隔離不了任何已知變動源，套上去就是投機性複雜度。
> **分層與 Ports 要，模組邊界不要。** 若日後後台長出多個明確領域再議。

### HTTP Client 的硬規則

| # | 規則 | 為什麼 |
|---|------|--------|
| 1 | 用 **Spring 內建的 `RestClient`**（Boot 3.5 / Framework 6.2 已有），**不要用 `RestTemplate`**（維護模式） | 對映 D10「最小相依」—— **不得為此引入第三方 HTTP client** |
| 2 | **必須設定連線與讀取逾時** | 沒逾時就分不出「慢」和「掛了」，E1 無法正確呈現 |
| 3 | **禁止全域 retry 攔截器** | E2：結果未知**不得自動重送** —— 重送危險操作可能重複執行。查詢類要 retry 也必須逐一指定，**變更類一律不重試** |
| 4 | 錯誤必須**分類**後往上傳，不可壓成同一種 | E1（連不上／逾時）與 E2（送出後中斷、結果未知）的畫面行為**完全不同**；4xx 是業務錯誤要顯示服務端訊息，5xx 是故障 |
| 5 | 呼叫 Admin API 用的憑證**不得落 log**，錯誤訊息也不得回顯 | R10 |
| 6 | **不得把 Admin API 的原始回應直接透傳給前端** | 那等於把 Admin API 開到後台的存取範圍上（§2）；必須經過後台的授權過濾與 DTO 轉換 |

### 錯誤分類 → 畫面行為對照

| Adapter 收到 | 分類 | 畫面（`web-frontend.md` §3） |
|---|------|------|
| 連線被拒 / DNS 失敗 / 連線逾時 | **不可達** | 「無法連線到 crypto-node…」；變更類**拒絕送出** |
| 已送出但讀取逾時 / 連線中斷 | **結果未知** | 「結果未確認，請重新查詢確認後再重試」；**絕不自動重送** |
| 4xx（含服務端的合法範圍回報） | **業務錯誤** | 顯示服務端訊息（確認數範圍、重掃區間上界皆以其為準） |
| 5xx | **服務端故障** | 同「不可達」處置 |

> **第 2 與第 4 類最容易被寫成同一種。** 「連線逾時」與「送出後讀取逾時」在多數 HTTP client 裡是同一個 exception 型別，但**前者可以安全重試、後者絕對不行**。Adapter 必須區分並在型別上表達出來。

## 3. 業務資料唯一來源（R11）

**後台不得成為業務資料的第二個真實來源。**

| 資料 | 來源 | 後台可否持久化 |
|------|------|--------------|
| 租戶、地址、訂閱者、交易、事件 | **crypto-node 服務** | ❌ **不得保存可與服務端不一致的副本** |
| ① 使用者帳號 | 後台 | ✅ |
| ② 權限指派 | 後台 | ✅ |
| ③ 操作紀錄（含理由） | 後台 | ✅ |
| ④ 開通檢核狀態與隔離驗證紀錄 | 後台 | ✅ |

> ③④ 服務端不持有，所以後台是它們的唯一來源。①②③④ **以外的一律不得落地**。

### 界線（E17，最容易寫錯的一條）

後台**得讀取**服務端的變更紀錄用於顯示（例：下游經 API 新增／刪除地址，顯示操作者為 `sys`、理由「非本後台操作」），**但不得把它們寫入後台自有儲存** —— 一寫入就成了「可與服務端不一致的副本」。

**判準：** 這筆資料重新整理後是重新向服務端取得，還是從後台自己的表讀出來？後者 → 違規。

> **快取已決（2026-08-26）：首期不做跨請求快取**，允許的例外只有「單一請求內去重」（請求結束即消失，不構成第二真實來源）。
> 快取正是「第二個真實來源」最常見的偽裝 —— 它不叫資料庫、沒有 migration、review 時不像違規，但行為一模一樣。

## 4. 呼叫 Admin API 的錯誤處理契約

| 情境 | 必須的行為 | 來源 |
|------|-----------|------|
| **服務無回應／逾時** | 顯示「無法連線到 crypto-node，以下資料無法取得」；**絕不顯示空清單**（會被誤讀為「沒有資料」）。變更類操作**拒絕送出**並提示稍後重試 | E1 |
| **送出後連線中斷、結果未知** | 顯示「結果未確認，請重新查詢確認後再重試」；**絕不自動重送**（重送危險操作可能重複執行） | E2 |
| **部分成功**（地址匯入） | 顯示成功／已存在／被拒**三類筆數** + **被拒的完整逐筆清單含原因**；**明確告知已成功的部分不回滾** | E3、R8 |
| **服務端回報的限制** | 確認數合法範圍、重掃區間上界一律**顯示服務端回報的值**，後台**不自訂**；越界時**不提供強制執行選項** | E8、E14 |
| **併發編輯** | 後送出者顯示「此資料已被他人變更」並重新載入，**不得靜默覆蓋** | E7 |

> **E1 的「不得顯示空清單」是本專案最容易犯的錯**：多數 HTTP client 的錯誤處理會回一個空集合，UI 照樣渲染成「目前沒有資料」。**必須把「取得失敗」與「確實沒有」做成兩個不同的狀態**，一路貫穿到畫面（見 `web-frontend.md` §3）。

## 5. 授權判定在後端，不在前端

> **認證、第二因素、工作階段**的決議見 [`locked-decisions.md`](./locked-decisions.md) 三之二。本節只管**授權**。

前端隱藏按鈕是 **UX，不是安全邊界**。

- **每一個變更類端點都必須在後台後端重新判定**：操作者的權限級別（Viewer / Operator / Admin）+ 租戶範圍。
- **租戶範圍過濾必須在查詢條件裡**（`WHERE tenant_id IN (...)`），不是取回全部再於應用層或前端剔除。
  - 這與 crypto-node 的 **I8** 同源：範圍外的租戶**不得出現在任何清單、下拉選單或查詢結果**（R2）。
  - **地址反查若命中範圍外的租戶，只回報「不屬於你可操作的租戶」，不得揭露是哪一個。**
- **權限變更必須即時生效**，不得等下次登入（R4）；使用中被調降 → 下一次操作即拒絕（E12）。

> **Review 檢查點：** 看到任何回傳業務資料的端點，第一個問題是「**它有沒有依操作者的租戶範圍過濾，且過濾發生在查詢層**」。

## 6. 操作紀錄的寫入契約（R7）

**所有變更類操作**必須記錄：時間、**操作者（人）**、動作、影響的租戶、結果、理由（危險操作）。查詢類不記錄。

| 情境 | 操作者欄位 |
|------|-----------|
| 經本後台的變更 | 具體的人 |
| **非經本後台**（下游 API、過渡期命令列、後台上線前的既有狀態） | **`sys`**，理由「非本後台操作」——**不得留空，也不得以服務端身分冒充為人** |

**不納入操作紀錄的認證類事件**（明示的決定，不要自行擴充或縮減）：登入成功／失敗、帳號鎖定、**使用者自己完成的首次第二因素綁定**。

> 首次綁定發生在取得紀錄能力**之前**（Flow-A step2c），要求它留痕會產生無法滿足的循環依賴。
> **但 Admin 對他人做的第二因素重設、帳號建立與停用屬變更類，必須留痕** —— 差別在「誰對誰做」，不在動作名稱。

**憑證絕不入紀錄**（R10）：API Key、簽章金鑰、第二因素種子、**節點供應商網址**（內含憑證）一律不得出現在操作紀錄、錯誤訊息或匯出檔案。

## 7. 三個跨系統依賴（日曆風險，交期不由我們決定）

`backlog.md` 列了三個需要 **crypto-node 服務端**先交付的能力。**它們不是後台能繞過的**：

| # | 缺什麼 | 卡住什麼 |
|---|--------|---------|
| ① | 地址刪除 API 記錄發起者並可查詢 | T8 的地址移除 —— 否則答不出「誰刪的」 |
| ② | **逐台**節點狀態與逐台切換 | T13c-ii —— 否則無法判定全叢集是否切完（R19②） |
| ③ | nginx 內網邊界（或服務端信任代理標頭） | R13 的執行點（見 §2） |

**紀律：**
- 這三項在服務端交付前，**後台不得自行實作替代方案**（例如自己去猜哪台切了）。
- 依賴 ② 的過渡期作法已明訂（R19③）：UI 維持「顯示單台狀態 + 告知限制」，並明示「全叢集切換請洽後端工程師」。**能力交付後必須同時移除這句提示** —— 否則系統說已完成、文案說去找工程師，指引互相矛盾。
- 這三項的等待時間**不可與其他 TASK 的等待相抵**（企劃已標為日曆風險）。

> **② 有可能不需要服務端改程式**：既然對外由 nginx 收口，逐台狀態與逐台切換**可能純靠 nginx 設定達成**（對每個實例各開一條可定址路徑）。這歸 **OQ-9** 評估；若成立，日曆風險 ② 即消除。**這是值得優先驗證的一條**。

## 7.1 逐台能力（OQ-9 ⑥，部分決議 2026-08-26）

**已決：每個 crypto-node 實例在 `application.yml` 設定 `node-id`；node-id 衝突則拒絕啟動。**

⚠ **node-id 只回答「我是誰」，不回答「怎麼指定打給哪一台」** —— 後台把請求送給 nginx，落在哪台不是後台決定的。**設了 node-id 不等於解決 R17**，逐台切換仍需要一個定址手段。

**定址手段待確認，前提只有一個：三台是否各有穩定可定址位址（固定 host/port）？**

| 前提成立 | 前提不成立（容器動態排程、實例會漂移） |
|---|---|
| 走 **nginx 逐台路徑** —— 純設定，crypto-node 零程式碼變更 | 需要服務端提供逐台能力（原本的跨系統依賴②） |

**驗證方式（一個下午）**：請維運先在 nginx 開**兩條**路徑，後台各查一次，看回來的節點來源是否不同。成立 → 日曆風險②消除、T13c-ii 解鎖、切節點回到 M3 的 5 分鐘承諾內。**這是目前投報率最高的一條，值得優先做。**

> **走 nginx 路徑時必加的交叉檢查**：後台打 `/node-2/` 就要確認回應帶回的 node-id 是 `node-2`，不一致要顯示明確錯誤、**不得照樣渲染**。否則路徑或設定指錯時，畫面會顯示三筆看起來正常的資料而其中兩筆是同一台 —— **值班員會以為三台都切了**，正是 R17 要防的誤判換了個成因。

**實作細節（互斥怎麼做、狀態怎麼彙總）屬開發當下的判斷，不在本文預先鎖定。**
