> **本文管的是「怎麼工作」**：拓樸與已決的連接方式、**只有跨文件推論才得出的紅線**、待決事項的處置紀律。
> 業務規則與畫面行為的權威來源是 `plan/crypto-node-web/spec.md`（R# / E# / AC）—— 本文**不複述它**。

## 1. 拓樸與連接方式（已決，2026-08-26）

```
[瀏覽器]
   │ ① 前端 ↔ 後台後端（自訂契約）
   ▼
[nginx]  ← ⚠ 內網／VPN 邊界的唯一執行點（§2）
   │
   ▼
[crypto-node-web]        ← 同 repo 模組
   │ ② 內網 RESTful → /admin/**
   ▼
[crypto-node-service]    ← 業務資料的唯一真實來源
```

```
crypto-node/
├── crypto-node-flyway/     DB migration
├── crypto-node-service/    A 軌：鏈下索引與事件中繼
└── crypto-node-web/        B 軌：維運後台（前端 + 後台後端）
```

| 層 | 契約 | 誰擁有 |
|---|------|--------|
| ① 前端 ↔ 後台後端 | 本專案自訂，可自由演進 | 我們 |
| ② 後台後端 ↔ crypto-node | **既有的 Admin API**（[`event-contract.md`](./event-contract.md) §4） | crypto-node 服務端 |

> **後台是 Admin API 的新消費者，不是它的擁有者。** 需要 Admin API 新增能力 → 那是**服務端變更**，走 A 軌流程，不是在後台這邊繞過去。

## 2. ⚠ 最高紅線：內網邊界會靜默失效（R13a）

**這一條是本文存在的主要理由 —— 它讀單一文件讀不出來，是三份文件交叉才得出的結論：**

| 來源 | 說了什麼 |
|---|---|
| crypto-node 服務端 | `/admin/**` 只允許內網網段呼叫，**依連線來源位址判斷、忽略代理標頭** |
| brief 決議 3 | 對外由 **nginx** 搭配域名收口 |
| brief OQ-9（本輪已決） | 連接方式＝**內網 RESTful**，也就是**後台後端代為呼叫** |

三者合起來：

```
維運人員 → nginx → crypto-node
                ↑
        服務端看到的來源恆為 nginx／後台自己（落在內網網段）
        → 網段過濾對所有請求一律放行 → 保護等於不存在
```

**這是靜默失效：不會報錯、不會有 log、測試也不會紅。** 企劃已明文警告過（OQ-9「已知陷阱」），而本輪的決議**確認了它成立，不再是假設**。

### 三項硬規則（缺一不可）

1. **nginx 必須只允許內網／VPN 來源存取 `/admin/**`**。
2. **不得存在繞過 nginx 直達服務的路徑** —— 有一條就等於邊界不存在。
3. **服務端的網段過濾在此架構下不可再計入防線** —— 必須明文記錄在部署文件裡。

> **為什麼第 3 條要明文寫：** 不寫的話，會有人以為「還有兩道防線」而各自放鬆一點，最後一道都不剩。
> **不要因為「反正都在內網」而放鬆任何一項。**

### 對開發的直接要求

- **後台後端不得成為 Admin API 的公開代理。** 任何「把請求原樣轉發」的端點都是把 Admin API 開到後台的存取範圍上。
- **後台後端的授權判定不是「多一道防線」，它是唯一的那道。**
- R13 的驗收**不在後台側**（後台驗不到 nginx 設定），由**部署驗收**承接。實作時要明確標出「這一條我驗不到」，**不要假裝有測試覆蓋**。

## 3. 三條讀 spec 讀不出來的界線

spec 已經寫清楚該做什麼；下面三條是**容易讀成相反意思**的地方。

| # | 界線 | 為什麼容易搞錯 |
|---|------|--------------|
| 1 | **授權判定與租戶範圍過濾必須在後端、且在查詢條件裡**（`WHERE tenant_id IN (...)`），不是取回全部再剔除 | 前端已經藏了按鈕、服務端「看起來也有擋」→ 兩邊都覺得對方會做，實際上兩邊都沒做 |
| 2 | **後台得「讀取」服務端的變更紀錄用於顯示，但不得寫入後台自有儲存** | 一寫入就成了「可與服務端不一致的副本」（R11）。**判準：重新整理後是重新向服務端取得，還是從後台自己的表讀出來？後者＝違規** |
| 3 | **操作紀錄的「不記錄」清單是明示的決定，不得自行擴充或縮減**（R7 已列舉哪些認證類事件不納入） | 看起來像遺漏，會有人「順手補上」。補了會淹沒真正的變更紀錄 |

**快取已決（2026-08-26）：首期不做跨請求快取**，允許的例外只有「單一請求內去重」（請求結束即消失，不構成第二真實來源）。

> 快取是「第二個真實來源」最常見的偽裝 —— 它不叫資料庫、沒有 migration、review 時不像違規，但行為一模一樣。

## 4. 三個跨系統依賴（交期不由我們決定）

`backlog.md` 列了三個需要 **crypto-node 服務端**先交付的能力（地址刪除發起者、逐台節點狀態與切換、nginx 內網邊界）。**細節去讀 backlog 的「日曆風險」段落。**

**紀律（這才是範本的事）：**

- 服務端交付前，**後台不得自行實作替代方案**（例如自己去猜哪台切了）。
- 過渡期作法若已在 spec 明訂（如 R19③ 的「請洽後端工程師」提示），**能力交付後必須同時移除那句提示** —— 否則系統說已完成、文案說去找工程師，指引互相矛盾。
- 這三項的等待時間**不可與其他 TASK 的等待相抵**。

## 5. 逐台能力（OQ-9 ⑥，部分決議 2026-08-26）

**已決：每個 crypto-node 實例在 `application.yml` 設定 `node-id`；node-id 衝突則拒絕啟動。**

⚠ **node-id 只回答「我是誰」，不回答「怎麼指定打給哪一台」** —— 後台把請求送給 nginx，落在哪台不是後台決定的。**設了 node-id 不等於解決 R17。**

**定址手段待確認，前提只有一個：三台是否各有穩定可定址位址（固定 host/port）？**

| 前提成立 | 前提不成立（容器動態排程、實例會漂移） |
|---|---|
| 走 **nginx 逐台路徑** —— 純設定，crypto-node 零程式碼變更 | 需要服務端提供逐台能力（原本的跨系統依賴②） |

**驗證方式（一個下午）**：請維運先在 nginx 開**兩條**路徑，後台各查一次，看回來的節點來源是否不同。成立 → 消掉一個日曆風險。**這是目前投報率最高的一條。**

> **走 nginx 路徑時必加的交叉檢查**：後台打 `/node-2/` 就要確認回應帶回的 node-id 是 `node-2`，不一致要顯示明確錯誤、**不得照樣渲染**。否則畫面會顯示三筆看起來正常的資料而其中兩筆是同一台 —— 值班員會以為三台都切了。

**互斥與狀態彙總怎麼實作，屬開發當下的判斷，本文不預先鎖定。**
