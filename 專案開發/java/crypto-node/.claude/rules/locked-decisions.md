> 這些是開發企劃書 §1 決策摘要中**已定案**的項目，每一條都有完整推導與取捨分析。
> **AI 不得在實作中「順手改回原案」或引入被明確排除的東西。** 要翻案 → 停手，回報使用者走決策流程。

## 一、範圍被**移除**的（做了就是超出範圍）

| # | 決策 | **不要做什麼** |
|---|------|--------------|
| **D2** | 掃塊通道：只做 HTTP Polling，統一 10 秒 | ❌ **不做 WebSocket**。WS 延後到確認 SLO 不達標才評估。看到 `eth_subscribe` / WS client 相關程式碼 = 越界 |
| **D16** | 投遞模型：**Pull-only** | ❌ **不做 Webhook 推送**。不做 Dispatcher、HMAC 簽章、指數退避重試、熔斷、手動重發 API。下游來拉，游標自持 |
| **D17** | 掃描範圍：只掃已確認區塊 `head - N` | ❌ **不做 Reorg 回溯**、不做確認數狀態機、**不實作 `payment.reorged` 事件**、不做雜湊鏈校驗。改以每日重掃稽核偵測 |
| **D4** | `confirmations` 不存 DB | ❌ 不新增 `confirmations` 欄位、不做每塊批次 UPDATE。讀取時計算：`chain_head - block_number + 1` |
| **D3** | 資料來源：`eth_getLogs` 按合約白名單批次撈取 | ❌ 不掃全區塊、不逐筆抓 Receipt 做主路徑（代幣路徑不需要 —— EVM revert 時丟棄所有 Log，`getLogs` 天然只回成功交易） |

> **D17 的連鎖效應**：狀態機簡化為 `detected`（選用）→ `confirmed`。**`pending` 與 `reorged` 都不存在。** 若在程式碼或 Schema 看到這兩個狀態，那是 bigpicture 的殘留，應清除。

## 二、架構形態被**鎖定**的

| # | 決策 | 規格 |
|---|------|------|
| **D11** | 單體 | **單一程式碼庫、單一部署產出物**，靠設定與旗標決定角色（`--role=scanner --chain=BSC`）。三鏈 Scanner 從同一個 image 啟動。❌ 不拆微服務 |
| **D10** | 技術棧 | PostgreSQL + **Spring Modulith**（見下方 D19）。❌ **不引入 web3j、不引入 MQ、不引入 Quartz** —— JSON-RPC 直接用 HTTP client 打，排程用 Spring 內建 |
| **D19** | 架構 | **六角架構 + Spring Modulith 模組化單體**（使用者於 2026-08-17 核可）。Domain 零框架、Ports 反轉依賴、模組以 `internal` 封裝、跨模組走事件。規範見 [`architecture.md`](./architecture.md) |
| **D13** | 輪詢間隔 | **統一 10 秒**（所有鏈一致），搭配 Receipt 驗證。❌ 不依各鏈出塊時間分別調整 —— 成本結構的決定性取捨 |
| **D14** | 延遲 SLO | **≤ 30 秒（P95）**（放寬自原本的 5 秒，是 D13 的前提） |
| **D15** | 租戶模型 | **多租戶為核心需求（已定案）**。資料模型與對外契約皆含 `tenant_id` |
| **D9** | 開發順序 | **縱向切片**：BSC 端到端打通 → ETH → TRON。❌ 不做橫向開發（三鏈掃塊 → 狀態機 → 投遞） |

> **D9 的意義**：第 2 週就要能發現整合問題。若你發現自己在「先把三條鏈的 Adapter 都寫完」，那是橫向開發，停下來。

## 三、⚠ 執行環境版本：本範本覆蓋 D18

| 來源 | 版本 |
|------|------|
| **本範本（以此為準）** | **Java 21 + Spring Boot 3.5** |
| plan **D18** | Java 21 + Spring Boot **4.1** |

**Java 21 兩邊一致，只有 Boot 版本不同。** 使用者於 2026-08-17 明確指定 3.5，本範本據此建立。

**實作影響：**
- 依賴一律鎖 **Boot 3.5.x BOM**；對應 **Spring Framework 6.2**、Jakarta EE 10。
- **不要抄 plan D18 或網路上的 Boot 4 / Spring Framework 7 寫法**（Boot 4 移除或改名的 API 在 3.5 仍在；Boot 4 才有的 API 在這裡不可用）。
- plan D18 記載的背景（3.5 OSS 支援已於 2026-06-25 隨 3.5.16 終止；無商業訂閱即無後續安全修補）**仍然成立**，只是使用者接受了這個取捨。若使用者問起，如實轉述，不要自行改版本。
- 日後若決定改回 4.1 → 那是**獨立的升級 TASK**，走完整流程，不是順手改版本號。

---

### D19 補充：Spring Modulith 是核可的例外，不是開了引入相依的口

- **為什麼核可**：本專案已因 Boot 版本問題耗費一輪決策成本（§3）。六角架構 + Modulith 的目的是讓**下一次**框架升級只衝擊最外層 Adapter，Domain 零變更。這是對抗「框架升級無限輪迴」的結構性解法。
- **D10「最小相依」原則仍然有效**。Modulith 是**指名核可**的單一例外，不代表其他相依可以比照援引。新增任何第三方相依仍須在 plan §2 說明理由。
- **Modulith 版本由其 BOM 對齊 Boot 3.5.x**。S01 實作時查證當下相容版本，不要憑印象填版本號。
- **⚠ Modulith 的事件機制與 I1 有直接衝突**：`@ApplicationModuleListener` 是 `AFTER_COMMIT` + `REQUIRES_NEW`，而 I1 要求區塊四項寫入在單一事務。**區塊寫入路徑不得用 Modulith 事件跨模組拆開**——詳見 `architecture.md` §4。這是套用這套架構時最容易踩的坑。
- **模組切分尚未定案**：plan 沒有定義模組邊界。`architecture.md` §3 提出了依「不變量歸屬」推導的提議，**S01 實作前必須列為 OQ 請使用者確認**。

**Out of Scope（不得為它們鋪路）**：帳務／訂單比對、出金與私鑰、監控圖表儀表板、告警管道設定、業務客服介面、下游自助開通、對外網開放、改變下游 `/v1/events` 取件方式。

**已決（開發端，2026-08-26）**：

| 決議 | 內容 |
|------|------|
| **前端技術棧** | **Vue 3 + Element Plus + Pinia + Vite**。理由：組織既有 Vue 心智模型可用、Element UI → Element Plus 有遷移對應、admin 生態 Vue 較強；**Vue 2 → Vue 3 是升級不是換框架** |
| **前端落點** | **同 repo**：`crypto-node-web/`，與 `crypto-node-service`、`crypto-node-flyway` 同層。理由：前後端契約變更可在同一個 commit / MR 完成，避開 `cx-sports` 的 Flyway 獨立 repo 那種「自己 repo 全綠、另一邊有問題」的不同步 |
| **第二因素** | **TOTP 驗證器 App**（企劃決議 6）。種子**加密後存 DB**、漂移容許 **±30 秒**、**不做備援碼**（備援碼是自助繞過第二因素的管道，牴觸 **E5**） |
| **工作階段管理** | **Spring Session + JDBC**（存既有 PostgreSQL，**不引入 Redis**，D10）。⚠ **禁止 stateless JWT** —— R15／R4／AC-49 都要求「立刻失效」，JWT 結構上做不到 |
| **讀取效能手段** | **首期不做跨請求快取**（只允許單一請求內去重）。首期一個租戶、使用者個位數 —— 先量再優化 |
| **逐台能力（部分）** | 各實例以 `application.yml` 的 **`node-id`** 標明身分，**node-id 衝突則拒絕啟動**。⚠ node-id 只回答「我是誰」，**不回答「怎麼指定打給哪一台」** —— 定址手段待確認，見 [`web-integration.md`](./web-integration.md) §7.1 |
| **後台與服務的連接方式** | **內網 RESTful**（後台後端代為呼叫 Admin API）。⚠ **這正是企劃警告的「代為呼叫」路徑** —— 確認 R13a 成立：服務端網段過濾對後台永遠放行，**nginx 三項成為唯一防線，後台後端的授權判定不是「多一道」而是那一道**。實作要求見 [`web-integration.md`](./web-integration.md) §2.5 |

> ⚠ **隨之而來的最高風險：抄到 Vue 2 寫法。** 組織有兩個 Vue 2 專案在旁邊、網路教學也大量是 Vue 2 —— 這與 Boot 3.5 誤抄 Boot 4 是同一類錯誤。對照表見 [`web-frontend.md`](./web-frontend.md) §1，實作模式見 [`/vue3-console`](../skills/vue3-console/SKILL.md)。

## 四、與這些決策相關的常見誤判

| 你可能想做 | 為什麼不行 |
|-----------|-----------|
| 「加個 WebSocket 會更即時」 | D2 明確延後；SLO 是 30 秒（D14），Polling 足夠。加了就是砍不掉的一整類 bug |
| 「Webhook 推送對下游比較方便」 | D16 已改 Pull-only，理由是多租戶下 Dispatcher 的重試／熔斷／公平調度成本過高。下游拉取同時是災難復原手段 |
| 「Reorg 總得處理吧」 | D17：只掃已確認區塊，**沒有東西會被推翻**。Reorg 偵測改以每日重掃稽核達成 |
| 「confirmations 存起來查詢比較快」 | D4：每塊全表寫入放大。讀取時計算即可 |
| 「用 web3j 比較省事」 | D10：只需要少數幾個 JSON-RPC 方法，引入整個 web3j 是過度相依，且 TRON 用不到 |
| 「先把三條鏈都接完再做事件」 | D9：縱向切片。BSC 沒端到端跑通前不要碰 ETH |
| 「拆成 scanner 服務和 api 服務比較乾淨」 | D11：資料模型完全共用，拆分只增加部署與版本一致性負擔。**要邊界請用 Modulith 模組**（D19），那是「拆分成本為零」的版本 |
| 「Domain 直接當 JPA Entity 可以省一次映射」 | D19：Domain 一旦被 `jakarta.persistence` 綁死，整套架構的價值歸零 |
| 「模組間一律用事件解耦」 | 通則對，但 **I1 優先**。區塊四項寫入必須同事務同步，見 `architecture.md` §4 |
| 「Modulith 有 Outbox，`events` 表是不是多餘的」 | 兩者用途完全不同：Registry 管模組間內部事件，`events` 表是**對外契約**的載體與下游游標依據 |
| （B 軌）「後台存一份租戶清單查詢比較快」 | 違反 R11 —— 後台不得成為業務資料的第二個真實來源。且已決議**首期不做跨請求快取** |
| （B 軌）「用 JWT 比較現代、不用查 DB」 | 已決 Spring Session。R15／R4／AC-49 都要求立刻失效，JWT 唯一的優點正好被需求抵銷 |
| （B 軌）「給個備援碼比較不會被鎖在外面」 | 那是自助繞過第二因素的管道，牴觸 **E5** |
| （B 軌）「設了 node-id 就解決 R17 了」 | node-id 只回答「我是誰」，**不回答「怎麼指定打給哪一台」**。逐台切換仍需定址手段 |
| （B 軌）「服務端已經擋了內網，後台不用再判權限」 | **nginx 之後那層保護靜默失效**（R13a）。且已決議走內網 RESTful ＝代為呼叫，服務端對後台**永遠放行**。後台的判定是唯一的那道 |
| （B 軌）「反正都在內網，nginx 那幾條可以先簡單做」 | 內網 RESTful 讓服務端那層失效後，**nginx 就是唯一邊界**。放鬆等於對外開放 Admin API |
| （B 軌）「加個 retry 讓串接更穩」 | E2：結果未知**不得自動重送**。變更類一律不重試（`web-integration.md` §2.5） |
| （B 軌）「引入 OkHttp / Feign 比較好用」 | D10 最小相依。Boot 3.5 內建 `RestClient` 就夠（**不要用 `RestTemplate`**，維護模式） |
| （B 軌）「前端把按鈕藏起來就好」 | 前端隱藏是 UX 不是安全邊界，後端必須重新判定 |
| （B 軌）「用組織熟悉的 Vue 2 最快」 | Vue 2 已 EOL（2023-12-31）。已決議用 **Vue 3**（`web-frontend.md` §1） |
| （B 軌）從 cx-sports / crypto-payment 複製 Vue 元件過來 | 那兩個是 **Vue 2**。觀念可參考，**程式碼不可直接抄** —— Options API、`filters`、`.sync`、Vuex 在 Vue 3 都不可用 |

## 五、翻案流程

若實作中發現某個鎖定決策**確實**站不住腳（例如 Polling 真的達不到 SLO）：

1. **停手，不要私自改。**
2. 把證據整理成 OQ：實測數據 + 影響範圍 + 建議選項。
3. 回報使用者，由其決定是否走決策變更。
4. 決策若變更 → **回頭更新開發企劃書**對應的 D 編號，並在本檔同步。文件不更新的翻案不算數。
