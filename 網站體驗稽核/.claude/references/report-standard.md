# 報告結構契約與撰寫規範

> **用途：** `report-writer` 產出 `report.md` 的唯一格式依據。搭配 `templates/report-template.md` 使用。

---

## 1. 讀者假設

報告有兩類讀者，結構必須同時服務兩者：

| 讀者 | 只看 | 需要什麼 |
|---|---|---|
| 決策者（PM / 老闆） | 前 1 頁 | 現況一句話、最該先修的三件事、Quick Wins、要花多少力氣 |
| 執行者（工程師 / 設計師） | Finding 明細 | 改哪個檔案／元件、改成什麼、憑什麼這樣說（證據） |

**推論：** 前 1 頁禁止出現技術細節與選擇器；Finding 明細禁止只寫抽象結論。

---

## 2. 章節結構（順序固定）

```
# <站點名稱> UX 稽核報告

## 摘要（Executive Summary）
## 最該先修的三件事
## Quick Wins（低成本高效益）
## Finding 總覽（表格）
## Finding 明細
## Journey 走查紀錄
## 稽核限制與未覆蓋範圍
## 附錄：稽核資訊
```

各章節規範：

### 摘要
- **≤ 200 字**，純白話，不用專業術語。
- 必含：稽核了什麼範圍、整體印象一句話、問題集中在哪 2~3 個領域、有無阻斷級問題。
- **禁止**寫成「本報告分析了……」這類無資訊量的開場。直接講結論。

### 最該先修的三件事
- 三條，每條一句話，格式：`<問題現象> → <建議動作> → <預期效果>`。
- 依 `references/severity-priority.md` §4 挑選。
- 每條附對應 Finding id 連結。

### Quick Wins
- 表格：`id / 問題 / 怎麼改 / effort`。
- 依 `severity-priority.md` §3 挑選。沒有就誠實寫沒有。

### Finding 總覽
一張表，依 Priority 排序：

| Priority | ID | Severity | Category | 問題（title） | Effort | 位置 |
|---|---|---|---|---|---|---|

- `位置` 欄寫頁面名稱 + viewport，不要貼完整長 URL（完整 URL 在明細裡）。

### Finding 明細
每條 Finding 一個 `###` 小節，順序同總覽表。格式：

```markdown
### FND-001 · <title>

| | |
|---|---|
| Priority / Severity | P0 / Blocker |
| Category | Navigation |
| 出現於 | <頁面名稱> · <viewport> · [<URL>](<URL>) |
| Persona / 步驟 | 首次到訪者 · 註冊流程第 2 步 |
| Effort / Confidence | S / High |

**觀察到什麼**
<observed 原文>

![<說明>](evidence/screenshots/FND-001-xxx.png)

**為什麼這是問題**
<why_it_hurts 原文，含準則 ID>

**建議怎麼改**
- **改哪裡：** <what>
- **改成什麼：** <how>
- **預期效果：** <expected_effect>
```

- **截圖必須以 Markdown 圖片語法內嵌**，路徑為相對於 `report.md` 的相對路徑，讓報告在 GitLab／GitHub／VS Code 直接看得到圖。
- 一條 Finding 內嵌 1~2 張圖為宜；更多證據以連結列出，不要把報告變成相簿。
- 若證據是 log／DOM，以程式碼區塊內嵌，**≤ 15 行**，長的放連結。

### Journey 走查紀錄
每條 Journey 一個小節：

```markdown
### <Persona> · <Journey 名稱> — <完成 / 完成但受阻 / 未完成>

目標：<成功條件>
實際步數：<n>（計畫 <m>）

1. **我想** <意圖> → **我看到** <畫面> → **我做了** <動作> → **結果** <結果> ⚠️FND-003
2. ...

結論：<一句話，這條路好不好走>
```

- ⚠️ 標記該步驟撞到的 Finding id。
- **這一章是報告的靈魂**，它證明了「這是真的有人走過一遍」而不是靜態檢查表。不得省略。

### 稽核限制與未覆蓋範圍
**誠實義務章節，不得美化。** 必須逐項列出：
- 沒走到的路徑與原因（不可逆操作、需憑證、卡驗證碼、需真實金流）
- 沒觀察的維度與原因（工具不可用、時間限制）
- 只觀察一次、無法重現的現象
- 使用測試帳號／特定裝置造成的代表性限制
- 本次未稽核的視窗尺寸／瀏覽器

### 附錄：稽核資訊
稽核日期、目標網域、模式（快掃／深度走查）、視窗矩陣、Persona 清單、瀏覽器與 MCP 版本、證據檔案數、被合併的 Finding id 對照、稽核期間對目標站造成的可逆變更與還原情況。

## 3. 寫作規範

**語言**
- 一律**繁體中文**。專有名詞（LCP、CLS、WCAG、DOM、CTA、hover）保留原文。
- 用**主動語態**、短句。避免「被認為是」「可能存在著一定程度的」這類軟化語。

**禁止用語（無法交辦的空話）**

| 禁止 | 改成 |
|---|---|
| 優化使用者體驗 | 把 X 從 A 改成 B |
| 提升易用性 | 在 X 加上 Y，讓使用者不必 Z |
| 改善視覺設計 | 把主 CTA 的對比從 2.1:1 提高到 ≥ 4.5:1 |
| 建議重新設計 | （拆成具體的數條可交辦改動；真的需要重構才在「最該先修」用一句話說明並列出理由） |
| 加強引導 | 在第 2 步上方加一行說明文案：「<具體文案建議>」 |
| 應符合最佳實務 | 依 [準則ID]，具體做法是 X |

**建議的寫法標準**
- `what` 必須能讓工程師**找到那個東西**：頁面 + 元件 + 可見文字或選擇器。
- `how` 必須是**動作**：加什麼、移到哪、改成什麼數值、文案寫什麼。給得出具體文案就直接給。
- `expected_effect` 必須**可觀測**：使用者少點 2 次、錯誤率下降、對比達 AA、LCP 降到 2.5s 內。
- 涉及商業取捨時（拿掉必填欄位、改價格呈現、動促銷版位）→ 寫成「建議 + 取捨說明」，把決定權留給使用者。

**不要做的事**
- 不要在報告裡替使用者決定產品方向。
- 不要引用沒實際量測的數字。
- 不要為了讓報告看起來豐富而重複同一個問題的不同表述。
- 不要在報告中出現帳密、Token、未遮蔽個資。
