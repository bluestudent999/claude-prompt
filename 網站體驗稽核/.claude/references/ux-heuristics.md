# UX 準則庫（Heuristics Catalog）

> **用途：** Finding 的 `why_it_hurts` 必須以 `[準則ID]` 開頭，ID 取自本表。這讓每條建議可追溯到公認準則，而非稽核者的個人品味。
> **用法：** 按需查閱，不要整份讀進 context。依你負責的維度只讀對應章節。
> **ID 不在表內時：** 用最接近的 ID，並在 `why_it_hurts` 內說明；**不要自創 ID**。若某類問題反覆出現且無對映，回報使用者建議擴充本表。

## NAV — 導航與資訊架構（heuristic-evaluator）

| ID | 準則 | 什麼算違反（要有的證據） |
|---|---|---|
| NAV-1 | **當前位置可知**：使用者隨時知道自己在哪 | 導航無選中態、無麵包屑、頁面標題與入口名稱不符（截圖） |
| NAV-2 | **分類互斥且窮盡**：一級分類不重疊、不遺漏 | 同一目標有多條入口且子項重複；或找不到明顯該有的分類（snapshot + 截圖） |
| NAV-3 | **標籤用使用者的語言**：不用內部術語、不用行銷造詞 | 導航項是自創名詞，無法從字面判斷內容（截圖 + 該頁實際內容對照） |
| NAV-4 | **回得去**：任何深頁都能一步回到主要入口 | 無麵包屑且 logo 不可點回首頁；流程頁移除全站導航後無退路（截圖） |
| NAV-5 | **搜尋可用且結果有用**：有搜尋則須能處理錯字、同義詞、空結果 | 搜尋常見詞得到 0 結果；空結果頁無建議與後續動作（截圖） |
| NAV-6 | **點擊深度合理**：主要轉換目標 ≤ 3 步可達 | 實走 Journey 記錄步數超標（逐步截圖） |
| NAV-7 | **深連結與返回鍵正常**：URL 可分享、瀏覽器上一頁行為符合預期 | `navigate_page_history` 後狀態錯亂或跳出流程（前後截圖） |

## FRM — 表單與輸入（heuristic-evaluator）

| ID | 準則 | 什麼算違反 |
|---|---|---|
| FRM-1 | **只問必要的**：每個必填欄位都有存在理由 | 註冊要求非必要欄位（生日、性別、地址）且無說明用途（截圖） |
| FRM-2 | **標籤持續可見**：不用 placeholder 當唯一標籤 | 輸入後標籤消失、無法確認該欄位是什麼（輸入前後截圖） |
| FRM-3 | **格式期待前置說明**：密碼規則、電話格式在輸入**前**就講清楚 | 規則只在錯誤後才出現（截圖序列） |
| FRM-4 | **即時且針對性的驗證**：錯誤指向具體欄位並說明如何修正 | 錯誤訊息只有「輸入有誤」、或整表單只在送出後一次性報錯（截圖） |
| FRM-5 | **輸入不被清空**：驗證失敗後保留已填內容 | 送出失敗後欄位被清掉（前後截圖） |
| FRM-6 | **正確的輸入型別與自動填入**：數字鍵盤、`autocomplete`、`inputmode` | 手機端填電話跳出全鍵盤；無 `autocomplete`（DOM 片段 + 手機截圖） |
| FRM-7 | **多步流程有進度指示**：知道共幾步、現在第幾步、能否回上一步 | 無步驟指示或無法回退修改（截圖） |
| FRM-8 | **必填/選填標示一致**：全站同一套標示法 | 有的標星號、有的寫「(選填)」、有的沒標（多頁截圖） |

## FBK — 回饋、狀態與錯誤處理（heuristic-evaluator）

| ID | 準則 | 什麼算違反 |
|---|---|---|
| FBK-1 | **每個動作都有回應**：點了就要有反應（≤ 100ms 視覺回饋） | 點按鈕後無任何變化，使用者不知有沒有生效（截圖 + trace） |
| FBK-2 | **等待有狀態指示**：> 1 秒的操作要有 loading／骨架屏 | 白畫面等待、無 loading（截圖 + `performance_*` 實測秒數） |
| FBK-3 | **錯誤訊息說人話並給出路**：說明發生什麼 + 下一步怎麼辦 | 顯示技術錯誤碼、`undefined`、英文堆疊（截圖 + console log） |
| FBK-4 | **成功有確認**：完成後明確告知結果與後續 | 送出後直接回首頁，不知道成功了沒（截圖） |
| FBK-5 | **空狀態有用**：無資料時說明原因並提供行動 | 空白區塊或只寫「無資料」（截圖） |
| FBK-6 | **無聲失敗零容忍**：前端錯誤不得只出現在 Console | Console 有 error 但畫面無任何提示（console log + 截圖） |

## CTL — 使用者控制與自由（heuristic-evaluator）

| ID | 準則 | 什麼算違反 |
|---|---|---|
| CTL-1 | **可撤銷**：破壞性動作可復原，或至少有二次確認 | 刪除無確認、無復原（截圖） |
| CTL-2 | **可退出**：任何流程都能中途離開且不失資料 | 無關閉鈕的彈窗、離開流程即清空已填（截圖） |
| CTL-3 | **不強迫**：不用強制彈窗／強制註冊阻斷瀏覽 | 首屏立刻蓋滿註冊牆或多個彈窗疊加（截圖） |
| CTL-4 | **不劫持預期行為**：不擅自改捲動、返回鍵、新開視窗規則 | 站內連結全部新開分頁、捲動被接管（前後截圖） |

## CNT — 內容與微文案（heuristic-evaluator）

| ID | 準則 | 什麼算違反 |
|---|---|---|
| CNT-1 | **首屏答得出三問**：這是什麼、對我有什麼用、我該做什麼 | 首屏只有大圖與空泛標語（不滾動截圖） |
| CNT-2 | **按鈕文案描述結果**：不用「送出」「確定」「更多」 | 多個按鈕都叫「查看更多」，無法區分（截圖） |
| CNT-3 | **關鍵資訊不隱藏**：價格、費用、條件、期限不埋在小字或彈窗深處 | 需點兩層才看到總費用（截圖序列） |
| CNT-4 | **可掃讀**：段落短、有小標、重點在前 | 大段無層次文字牆（截圖） |
| CNT-5 | **術語有解釋**：專業名詞首次出現時說明 | 直接用專業縮寫且無說明（截圖） |
| CNT-6 | **語言與時態一致**：不混語言、不混稱謂、無未翻譯字串 | 中文頁面出現 `Submit`／未翻譯的 key（截圖） |

## VIS — 視覺設計與版面（visual-critic）

| ID | 準則 | 什麼算違反 |
|---|---|---|
| VIS-1 | **視覺層級對映重要性**：主要行動點最顯著 | 主 CTA 與次要按鈕同權重、或次要按鈕更醒目（截圖） |
| VIS-2 | **一頁一個主要行動**：不並列多個等權 CTA | 首屏 4 個同樣顯眼的按鈕（截圖） |
| VIS-3 | **群組靠鄰近性表達**：相關元素靠近、無關元素分開 | 標籤與其輸入框距離大於與鄰欄距離（截圖 + 量測值） |
| VIS-4 | **間距有節奏**：同層級元素間距一致 | 同一清單各項間距不一（截圖 + `evaluate_script` 量測） |
| VIS-5 | **可讀性**：正文字級與行高足夠、行寬不過長 | 正文 < 14px、行高 < 1.4、單行超過 100 字元（DOM computed style） |
| VIS-6 | **對比足夠**：文字與背景對比達標（見 A11Y-1） | 淺灰字在白底、文字壓在圖上（截圖 + 對比值） |
| VIS-7 | **無版面破損**：不重疊、不溢出、不截斷 | 元素互相覆蓋、橫向捲動、文字被切掉（截圖，特別是手機） |
| VIS-8 | **無內容位移（CLS）**：載入過程不跳動 | 圖片無尺寸保留導致內容位移（trace 的 CLS 值 + 前後截圖） |
| VIS-9 | **狀態視覺化**：hover／focus／disabled／selected 可分辨 | 按鈕無 hover／focus 樣式（`hover` 前後截圖） |

## CON — 一致性與慣例（heuristic-evaluator / visual-critic）

|---|---|---|

## MOB — 行動裝置與觸控（visual-critic）

| ID | 準則 | 什麼算違反 |
|---|---|---|
| MOB-1 | **觸控目標足夠大**：可點區 ≥ 44×44 px，彼此不擠 | 量測到 < 44px 或相鄰間距 < 8px（`evaluate_script` 量測 + 截圖） |
| MOB-2 | **無橫向捲動**：內容寬度不超出視窗 | 手機視窗出現水平捲軸（截圖 + `document.scrollWidth` 量測） |
| MOB-3 | **固定元素不遮擋**：固定頁首／頁尾／浮動客服不蓋住內容或按鈕 | 送出按鈕被浮動元素蓋住（截圖） |
| MOB-4 | **鍵盤彈出後仍可操作**：輸入時看得到欄位與送出鈕 | 聚焦輸入框後畫面被鍵盤遮蔽（截圖） |
| MOB-5 | **不依賴 hover** | 關鍵資訊只在 hover 時顯示，觸控裝置取不到（桌機／手機截圖對照） |
| MOB-6 | **手機版功能不縮水**：桌機有的關鍵功能手機也要有 | 手機版找不到桌機才有的篩選／功能（兩版截圖對照） |

## PRF — 效能與穩定性（a11y-perf-inspector）

> **鐵律：** 任何效能 Finding **必須**附 `performance_*` 或 `list_network_requests` 的**實測數字**。禁止「感覺很慢」。

| ID | 準則 | 門檻 / 什麼算違反 |
|---|---|---|
| PRF-1 | **LCP**（最大內容繪製） | > 2.5s 為 Major；> 4s 為 Blocker（trace 數值） |
| PRF-2 | **CLS**（內容位移） | > 0.1（trace 數值 + 位移前後截圖） |
| PRF-3 | **INP / 互動延遲** | > 200ms（trace 數值） |
| PRF-4 | **無 Console 錯誤** | 出現 JS error（console log 原文） |
| PRF-5 | **無失敗請求** | 4xx／5xx／CORS 失敗（network 記錄，含 URL 與狀態碼） |
| PRF-6 | **資源合理** | 單張圖 > 500KB、未壓縮、尺寸遠大於顯示尺寸（network 記錄 + 顯示尺寸量測） |
| PRF-7 | **弱網可用** | `emulate_network` 降速後主要流程是否仍可完成（降速前後截圖） |

## 準則使用紀律

1. **一條 Finding 對映一個主要準則 ID**。牽涉多條時選最根本的那個，其餘在 `why_it_hurts` 內文提及。
2. **不要為了套準則而套**。準則是用來解釋「為什麼這是問題」，不是問題本身。若你能寫清楚使用者付出什麼代價，準則 ID 自然對得上；若對不上任何 ID，先懷疑這是不是你的個人偏好而非真問題。
3. **通則不等於本站問題**。「本站沒有 XXX 最佳實務」若沒有觀察到實際造成的困難，不成立為 Finding。
