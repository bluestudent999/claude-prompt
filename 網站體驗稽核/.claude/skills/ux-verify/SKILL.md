# ux-verify — 回歸驗證

**用法**：`/ux-verify <上次報告路徑>`（例：`/ux-verify ux-reports/2026-07-31-cxsport/report.md`）

**核心原則**：**逐條重走、附新證據**。不看 code、不問開發、不憑「他說改好了」。判定的唯一依據是你**這次實際看到的**。

---

## Step 0 · Preflight

1. 讀上次報告，抽出所有 Finding 的 `id` / `severity` / `url` / `observed` / `recommendation`。
2. 確認 Chrome DevTools MCP 可用；確認環境模式（**應與上次相同**，不同則判定不可直接比較，要註明）。
3. **建新資料夾**：`ux-reports/<YYYY-MM-DD>-<站點簡稱>-verify/`
   > ⚠️ **絕不覆蓋舊 run 的證據**。新證據落在新資料夾，舊證據是判定「退步」的唯一基準。
4. 記錄上次報告的日期，計算間隔。

---

## Step 1 · 逐條重走（序列，你自己驅動瀏覽器）

對**每一條** Finding：

1. 導航到該 Finding 的 `url`（同一個 viewport）。
2. 重跑該 Finding 對應的觀察動作：
   - 視覺／版面類 → `take_screenshot` + 重抓量測包中的相關項目（要拿到**新的數字**）
   - 表單／流程類 → 重走該步驟，包含當初的試錯條件
   - 效能類 → 重跑 `performance_*` 拿**新的 LCP/CLS/INP**
   - A11Y 類 → 重抓 DOM / 重按 Tab
3. **把新觀察與舊 `observed` 逐項對照**，判定：

| 判定 | 條件 |
|---|---|
| **已修復** | 舊 `observed` 描述的現象已不存在，且新證據可證明 |
| **部分修復** | 現象減輕但未消除（例：對比從 2.1:1 升到 3.8:1，仍未達 4.5:1） |
| **未修復** | 現象照舊 |
| **退步** | 該處變得更差，或修這個弄壞了別的（**最高優先回報**） |
| **無法複驗** | 頁面／流程已改版，原場景不存在（不算已修復，要說明現在長怎樣） |

4. **每個判定都必須附新證據**。「看起來改好了」不算。

> **序列執行，不要平行**：你在驅動同一個瀏覽器（`observation-protocol.md` §2）。

---

## Step 2 · 順手抓新問題

重走過程中一定會看到上次沒有的問題（改動引入的、或上次沒覆蓋到的）。

- **開新 id，延續上次的號段**（上次到 FND-023 → 新的從 FND-024 開始）。**絕不重用舊 id**，否則歷史對照會亂。
- 新 Finding 走完整流程：符合 `evidence-discipline.md` §3 契約，並過守門。
- 但**不要藉機把整站重新稽核一遍**——那是 `/ux-audit` 的事。只收「重走路徑上撞到的」。

---

## Step 3 · 評估與守門（只針對新 Finding）

- 新 Finding → 平行調用評估角色（id 號段接續）→ 平行跑 `evidence-auditor` + `recommendation-reviewer`。
- 舊 Finding 的判定不需過建議守門（建議沿用上次的），但**新證據仍須過 `evidence-auditor` 的存在性檢查**。

---

## Step 4 · 產出對照報告

寫入 `<新 run>/report.md`，結構如下（**與標準報告不同，這是對照式**）：

```markdown
# <站點> UX 回歸驗證報告

- 上次稽核：<日期> · <上次報告路徑>
- 本次驗證：<日期> · 間隔 <n> 天
- 環境模式：<test / production>（與上次<相同 / 不同 → 不可直接比較>）

## 結論（≤ 100 字）
<修好了幾條、還剩幾條、有沒有退步。第一句就講結果。>

## 修復進度總覽
| 判定 | 數量 | 其中原 Blocker | 原 Major |
|---|---|---|---|
| 已修復 | n | n | n |
| 部分修復 | n | n | n |
| 未修復 | n | n | n |
| **退步** | n | n | n |
| 無法複驗 | n | n | n |

## ⚠️ 退步項目（若有，放最前面）
### FND-0xx · <title> — 退步
- **上次**：<舊 observed 節錄>
- **現在**：<新 observed>
- **新證據**：![](evidence/screenshots/xxx.png)
- **判斷**：<改動可能造成什麼>

## 逐條對照
| ID | 原 Severity | 判定 | 上次現象 | 現在現象 | 新證據 |
|---|---|---|---|---|---|

## 未修復項目明細（原 Blocker / Major 者完整寫）
<每條：原問題 + 新證據 + 原建議仍然有效 or 需調整>

## 本次新發現
<新 Finding，格式同標準報告的 Finding 明細>

## 驗證限制
- <無法複驗的原因、未重走的部分、環境差異>

## 附錄
- 上次報告路徑、本次證據清單、本次產生的交易資料編號
```

---

## Step 5 · 回報

```
回歸驗證報告：<路徑>
上次稽核：<日期>（間隔 <n> 天）
已修復 n / 部分修復 n / 未修復 n / ⚠️退步 n / 無法複驗 n
原 Blocker：<n> 條中修好 <n> 條
本次新發現：<n> 條
最需要注意：<退步項目，或還沒修的最高優先項>
```

---

## 判定紀律（最容易出錯的地方）

| ❌ | ✅ |
|---|---|
| 「看起來改好了」 | 附**新證據**，並與舊 `observed` 逐項對照 |
| 效能類憑感覺說變快了 | **重跑 trace 拿新數字**，兩次數值並列 |
| 對比從 2.1 升到 3.8 就算已修復 | 判**部分修復**——沒過 4.5:1 門檻就是還沒到 |
| 頁面改版了就算已修復 | 判**無法複驗**，並描述現在長怎樣、有沒有新問題 |
| 覆蓋舊資料夾的證據 | 新 run 新資料夾，舊證據是判「退步」的唯一基準 |
| 新問題重用舊 id | 延續號段開新 id |
| 順便把整站重稽核一遍 | 只收重走路徑上撞到的；要全面重稽核請跑 `/ux-audit` |
