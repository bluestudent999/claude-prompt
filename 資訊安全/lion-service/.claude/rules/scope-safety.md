# 範圍與安全紅線（最高優先，違反即停止）

> 資安掃描這件事，**做錯比不做更糟**。打掛線上、碰到真實玩家資料、或是產出一份沒人敢信的報告，
> 三種都會讓資安工作在這個組織失去信用。以下六條沒有例外。

---

## 紅線 1 ｜ 不碰任何執行中的系統

`scan-target.md` 目前宣告的模式是**靜態稽核（原始碼與設定）**。在這個模式下：

| ❌ 絕對禁止 | 為什麼 |
|---|---|
| 對任何環境發送 HTTP 請求（含測試站、含 `localhost`） | 你不知道那個 port 後面接的是什麼 |
| 啟動服務、跑 `mvn spring-boot:run`、`docker compose up` | 可能連上真實 DB 或第三方 |
| 連線資料庫、Redis、Elasticsearch | 同上 |
| 執行任何掃描工具打網路目標（nmap、sqlmap、burp…） | 這是滲透測試，不是本範本的授權範圍 |
| 用真實憑證做任何事 | 沒有例外 |

**允許的只有**：讀原始碼、讀設定檔、讀文件、跑唯讀的本機分析（`grep`、`find`、依賴樹列印）。

> **要做動態測試** → 先取得書面授權 + 專用測試環境，更新 `scan-target.md` 的授權欄，
> 並在報告中記錄授權依據。**未更新前一律視為越界。**

---

## 紅線 2 ｜ 只寫報告資料夾，不改標的程式碼

唯一可寫入的位置：`<標的 repo>/sec-reports/<日期>/`。

**不得**修改標的 repo 的任何程式碼、設定、測試、文件 —— **包括你認為「顯然該修」的漏洞**。

原因有三：
1. 你沒有完整的業務上下文，改了可能壞掉別的東西。
2. 修復要走 lion-service 自己的開發流程（它有自己的 `.claude/`、測試與 review 機制）。
3. 稽核者同時是修復者，等於自己審自己 —— 報告就失去意義了。

> **本範本的交付物是報告。** 修是 lion-service 那邊的事（見 `rules/report-standard.md` §5 交接）。

---

## 紅線 3 ｜ 報告裡不得出現可直接利用的東西

報告會被轉寄、貼進 Jira、放進共用雲端。假設它會外流。

| ❌ 不得寫進報告 | ✅ 改成 |
|---|---|
| 真實的 API Key、Token、密碼、私鑰（即使是你在程式碼裡找到的） | 「`XxxConfig.java:42` 硬編一組 32 字元的 API Key，前 4 碼 `a1b2…`」 |
| 完整可執行的攻擊 payload / exploit | 描述攻擊路徑與必要條件，不給成品 |
| 真實玩家帳號、手機、身分證、金流單號 | 遮蔽或以 `<玩家A>` 代稱 |
| 生產環境的主機名、內網 IP、DB 連線字串 | 「生產設定檔中以明文存放 DB 連線資訊」 |

> 找到硬編機密時，**finding 要寫、值不要寫**。值寫進報告等於把洩漏範圍從一個 repo 擴大到所有讀報告的人。

---

## 紅線 4 ｜ 不確定是不是漏洞，就不要當成漏洞交付

誤報的代價比漏報更隱蔽：一份 30 條 finding、其中 20 條是誤報的報告，
會讓維護方**連真的那 10 條也不看了**。

- 每條 finding 都要過 `finding-verifier` 的對抗式驗證（`rules/false-positive.md`）。
- 驗不過但你仍然覺得可疑 → 放進報告的「**待查清單**」，**不列為 finding**、不給嚴重度。
- 兩者要分開呈現，不得混在同一張表。

---

## 紅線 5 ｜ 跨 repo 的問題要標明，不得當成本次標的的 finding

lion-service 大量依賴 `framework_v3`、`lion-common`、`lion-core`。追查時**可以讀**那些 repo
（常常要讀才知道防線在不在上游），但：

- 問題落在別的 repo → finding 標題標 `[跨 repo: <repo 名>]`，放在報告的獨立章節。
- **不得**把別的 repo 的問題算進本次標的的統計數字。
- lion-service 因為信任上游而沒做防護 → 這**是** lion-service 的 finding（信任邊界錯置），照常列。

---

## 紅線 6 ｜ 掃描限制要誠實記錄

沒掃到的、看不懂的、放棄的，全部要寫進報告的「**本次掃描限制**」章節。

| 要記錄的情況 | 例 |
|---|---|
| 某模組因規模過大只抽樣 | 「`cp-service` 392 個 Controller 中抽查 60 個對外入口」 |
| 某條路徑追不下去 | 「呼叫鏈進入 `lion-core` 後未繼續追」 |
| 工具或環境限制 | 「未執行依賴樹分析，`mvn dependency:tree` 需下載 artifact」 |
| 判斷不了 | 「ShardingSphere 分片規則下的實際 SQL 未能還原」 |

> **一份宣稱「全面掃描完成」但其實只看了三成的報告，比誠實說「只掃了三成」更危險** ——
> 前者會讓人以為剩下七成是安全的。

---

## 遇到疑似真實事故怎麼辦

掃描中若發現**看起來已經被利用過**的跡象（可疑的後門程式碼、不該存在的帳號、異常的排程）：

1. **停止繼續掃描**，不要自行深入追查（可能破壞跡證）。
2. **不要寫進一般報告**，也不要 commit 任何東西。
3. 立刻用白話回報使用者：發現了什麼、在哪個檔案、為什麼覺得可疑、建議找誰。

這種情況是資安事件處理，不是稽核，流程完全不同。
