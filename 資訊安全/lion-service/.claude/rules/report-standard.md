# 報告標準

> **這份報告的讀者是 lion-service 的維護工程師，不是資安部門。**
> 成功的定義不是「找到多少漏洞」，是**對方看完知道先修哪一條、怎麼修、改完怎麼確認**。
> 一份沒人動手的報告，等於沒做。

---

## 1. 報告結構

```
<標的 repo>/sec-reports/<YYYY-MM-DD>/
├── report.md              主報告（決策者 + 工程師都讀這份）
├── recon.md               攻擊面盤點（過程產物，供追溯）
└── findings/
    ├── SEC-001-<slug>.md  逐條 finding（工程師照著修）
    └── ...
```

### report.md 的章節（順序不要改）

| # | 章節 | 內容 | 給誰看 |
|---|---|---|---|
| 1 | **一頁摘要** | 掃了什麼、找到幾條、最嚴重的三條是什麼、建議的處理順序 | 決策者 |
| 2 | **Finding 總表** | 編號／標題／嚴重度／信心／影響模組／狀態 | 全部 |
| 3 | **修復優先序** | 依「嚴重度 × 修復成本」排的建議順序，不是單純照嚴重度排 | 維護方排程用 |
| 4 | **逐條 Finding** | 連到 `findings/SEC-xxx.md` | 工程師 |
| 5 | **跨 repo 問題** | 落在 `framework_v3` / `lion-common` / `lion-core` 的，獨立成章 | 需協調的人 |
| 6 | **待查清單** | 驗不出來但可疑的，**不給嚴重度** | 下次掃描 |
| 7 | **已排除項目** | 看起來像漏洞但確認不是的，附理由 | 省下次的工 |
| 8 | **本次掃描限制** | 沒掃到什麼、為什麼 | 全部（誠實欄） |

> 第 6、7、8 章不是湊數。少了它們，讀者無法判斷「沒寫到的東西是安全的，還是沒看」。

## 3. 「修復方向」是最重要的一欄

維護方不會照著模糊建議做事。

| ❌ 空話 | ✅ 可執行 |
|---|---|
| 建議加強權限驗證 | 在 `OrderService.queryList` 入口以 session 的 `platformId` 覆寫 `query.platformId`，不接受請求帶入；或改走既有的 `XxxContext.getPlatformId()` |
| 建議升級依賴 | Jackson 2.9.5 → 2.9.10.x（同 minor，相容風險低）。**升級本身屬 `prompt-setup 版本管理` 的職責**，本報告只標版本與風險 |
| 建議做輸入驗證 | `platformId` 改用白名單列舉；`orderNo` 加 `@Pattern(regexp="[A-Z0-9]{16,32}")` |

**盡量對應到 lion-service 自己既有的規範條文**（`lion-service/.claude/rules/security.md`、`patterns.md`、`checks/`）。
對得上，維護方就知道這不是外人另訂一套標準，而是「你們自己的規則在這裡沒被遵守」—— 這種 finding 的接受度最高。

## 4. 修復優先序不是照嚴重度排

同樣是 CRITICAL，一個改三行、一個要重構整個模組，排程方式完全不同。

| 分類 | 意思 | 建議處理 |
|---|---|---|
| **立即修** | 高嚴重度 + 低修復成本 | 這週就做，通常是漏了一行檢查 |
| **排程修** | 高嚴重度 + 高修復成本 | 開票、拆任務、排版本 |
| **順手修** | 低嚴重度 + 低修復成本 | 併進下次相關改動 |
| **評估後決定** | 低嚴重度 + 高修復成本 | 記錄風險，可接受就明確接受 |

> 「評估後決定」那一格要寫清楚**不修的風險是什麼**，讓決策者能明確簽下「接受」。
> 沒寫清楚就等於把決定丟回去，然後永遠沒人決定。

## 5. 交接：報告怎麼變成修復

本範本**只產報告，不改 lion-service 的程式碼**（`rules/scope-safety.md` 紅線 2）。

交接方式：

1. 報告產在 `<標的 repo>/sec-reports/<日期>/`，隨 repo 一起看得到。
2. 維護方在 lion-service 自己的開發流程裡修 —— 它有自己的 `.claude/`（`security-reviewer`、`checks/`、測試與 review 機制）。
3. 每條 finding 已經寫成**可直接當工單**的形狀：位置、證據、修復方向、驗證指令齊備。
4. 修完之後跑 `/sec-verify <報告路徑>` 逐條複驗，標記「已修復／未修復／退步」。

> **不要在報告裡寫「我可以幫你修」。** 交付邊界就到報告為止。
