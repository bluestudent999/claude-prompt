# 誤報防治

> AI 做資安掃描最大的失敗模式不是漏掉漏洞，是**產出一堆看起來很合理的誤報**。
> 一份 30 條 finding、其中 20 條是誤報的報告，結果是維護方**連真的那 10 條也不看了**。
> 誤報不只浪費時間，它會摧毀整份報告的可信度。

---

## 1. 每條 finding 都要過對抗式驗證

掃描的 agent **不驗證自己的產出**。所有 finding 一律交 `finding-verifier`，
它的立場是**證明這條是誤報**，證不倒才放行。

驗證要逐項回答：

| 問題 | 答不出來就退回 |
|---|---|
| 這條路徑**真的打得到嗎**？對外入口是哪一個？ | 找不到入口 → 降級「待查」 |
| 上游有沒有**已經擋掉**？（Filter、Interceptor、AOP、閘道、nginx） | 擋掉了 → 誤報 |
| 框架有沒有**預設保護**？ | 有 → 誤報 |
| 這個輸入**真的可控**嗎？還是來自內部固定值？ | 不可控 → 誤報 |
| 觸發條件**現實嗎**？需要的前提是不是根本拿不到？ | 不現實 → 降嚴重度或降「待查」 |
| 有沒有**補償機制**讓影響不成立？（對帳、審核、風控） | 有 → 降嚴重度，並在 finding 寫明 |

---

## 2. 這個專案特別容易誤判的六種情況

| 情況 | 為什麼容易誤判 | 驗證方式 |
|---|---|---|
| **MyBatis `${}`** | 看到就想報 SQL injection，但很多是**欄名／表名／排序方向**，且值來自程式內固定列舉 | 追那個變數的來源。來自 request 且未白名單 → 真的；來自 enum／常數 → 誤報 |
| **`platformId` 沒檢查** | 很多查詢的 `platformId` 是在**上層 Service 或 AOP 由 session 覆寫**的 | 往上追到對外入口，確認是否被覆寫。沒覆寫才是 finding |
| **看似無認證的 Controller** | 認證可能在 `SecurityConfig` 的路徑規則、Filter、或 nginx，不在註解上 | 讀 `SecurityConfig` 與 filter chain，確認該路徑落在哪條規則 |
| **舊版依賴有 CVE** | CVE 存在 ≠ 這個專案受影響。多數 CVE 需要特定元件或設定 | 確認**受影響的類別／功能有沒有被實際使用**（見 `agents/dependency-cve-auditor.md`） |
| **`double` 用在金額** | 專案規範允許純統計用 `double` | 確認那個值是否會變成實際入帳金額 |
| **log 印了物件** | `toString()` 可能已排除敏感欄位（Lombok `@ToString.Exclude`、自訂 toString） | 讀那個類別的 `toString` 實作 |

---

## 3. 驗不過的東西放「待查」，不是丟掉

驗證失敗有兩種，處置不同：

| 結論 | 處置 |
|---|---|
| **確認是誤報**（上游擋掉了、輸入不可控） | 丟掉，不入報告。但若「為什麼不是漏洞」本身不直觀，寫進報告附錄的「**已排除項目**」，附一句理由 |
| **驗不出來**（追不到入口、看不懂框架行為、需要執行環境才知道） | 放「**待查清單**」：寫下懷疑什麼、卡在哪、要怎樣才驗得出來。**不給嚴重度、不算進統計** |

> 「已排除項目」看起來像廢話，其實很有價值 —— 下次掃描（或別人接手）不用再花時間重新懷疑同一件事。

## 4. 不重工靜態掃描工具

lion-service 已有 SonarQube（`sonar-project.properties`）。

| 類型 | 誰負責 | 本範本要不要報 |
|---|---|---|
| **規則型缺陷**：空指標、資源未關、硬編字串、圈複雜度、未使用變數 | Sonar | ❌ 不報。報了只是洗版 |
| **樣式型安全規則**：可被單一 grep 判定的寫法問題 | Sonar / SpotBugs | ⚠️ 只在「它確實構成可達的漏洞」時才報，並附攻擊路徑 |
| **業務邏輯型漏洞**：越權、包網商隔離、金流時序、回調偽造、狀態機繞過 | **本範本** | ✅ 這是本範本存在的理由 —— 靜態工具抓不到 |

> **判準**：這條 finding 如果 Sonar 自己就會報，而且報得比我清楚，那就不要報。
> 本範本的價值在「**需要理解業務才看得出來**」的那一類。

---

## 5. 信心分級要誠實標

嚴重度與信心**分開標**，不要用嚴重度去含糊表達不確定。

| 信心 | 意思 |
|---|---|
| **高** | 攻擊路徑完整追過，上游確認無防護，影響明確 |
| **中** | 路徑合理但有一段靠推論（例如未能確認某 Filter 的實際套用範圍） |
| **低** | 有疑慮但關鍵環節未驗證 → **這一級不該出現在 finding，應該在待查清單** |

> 一條「CRITICAL／信心低」的 finding 是自相矛盾的東西。真的那麼嚴重，就把它驗清楚再報。
