# 七條掃描軸

> 每條軸寫的是「**看什麼、怎麼判、什麼情況是誤報**」，不是完整的檢查清單。
> 實際的判準以 lion-service 自己的 `lion-service/.claude/rules/security.md`、`patterns.md`、`checks/` 為準 ——
> 「你們自己的規則在這裡沒被遵守」是接受度最高的 finding。

---

## 軸 1 ｜ 包網商隔離（最高優先）

**踩破的邊界**：3（資料範圍）｜**對應資產**：A2

### 看什麼

- `platformId` 的**來源**：從 session／token 取，還是從 request body／query 取？
- 有沒有統一的取得管道（Context、AOP、攔截器），還是各寫各的？
- 查詢條件裡的 `platformId` 會不會被請求覆寫？
- 跨平台的共用查詢介面（報表、統計、匯出）有沒有限制範圍？
- 快取的 key 有沒有帶 `platformId`（沒帶 = 跨平台污染）？
- ES 索引、MQ topic、檔案路徑有沒有按平台分隔？

### 怎麼判

**判準只有一句：請求方能不能影響「查到誰的資料」。**
能 → finding。不能（被 session 覆寫、被 AOP 強制）→ 誤報。

### 最容易誤報的地方

`platformId` 在下層 Service 看起來沒檢查，但**上層或 AOP 已經覆寫**。
一定要往上追到對外入口才能下結論。

---

## 軸 2 ｜ 認證、授權與越權

**踩破的邊界**：1、2、3｜**對應資產**：A5、A3、A4

### 看什麼

- 對外入口是否都落在認證規則內（注意：規則可能在 `SecurityConfig` 路徑比對、Filter、或 nginx，不在註解上）
- 功能級授權：角色能不能做這個動作
- **物件級授權**：能不能操作「不屬於自己的那一筆」（改 orderNo / userId 就拿到別人的）
- **代理層級越權**：沿 `agentId` 往上層或平行代理看資料
- 多套後台的權限模型是否一致（admin / agent / third / bet-station / boss / manage / bet-order）
- 內部介面的「內部」怎麼認定 —— nginx 之後還算不算內部？

### 怎麼判

物件級授權是最常漏的：**功能有權限、但沒檢查這筆資料是不是你的**。
判準：把請求裡的識別碼換成別人的，會不會成功？

---

## 軸 3 ｜ 金流與錢包

**踩破的邊界**：4｜**對應資產**：A1、A3

### 看什麼

- 金額是否可由請求方影響（前端傳金額 = 高風險）
- 餘額異動是否照「驗餘額 → 鎖行 → 扣減 → 寫流水」的順序，有無跳步
- 悲觀鎖 / 分散式鎖的覆蓋範圍，鎖的粒度對不對
- **冪等**：重複請求、重放、併發同時打會怎樣
- 負數、極大值、精度截斷（`BigDecimal` vs `double`、`RoundingMode`）
- 退款 / 撤單 / 補單路徑的權限與重複執行
- 派彩與結算的金額來源是否可竄改

### 怎麼判

參照 lion-service `lion-service/.claude/rules/security.md` 的金額章節與 `lion-service/.claude/checks/bigdecimal-rounding.md`、
`lion-service/.claude/checks/idempotency-orderno.md` —— 違反它自己訂的規則就是 finding。

### 誤報注意

規範允許純統計（筆數、頁數、耗時）用 `double`。要確認那個值會不會變成實際入帳金額。

---

## 軸 4 ｜ 注入與輸入處理

**踩破的邊界**：4、以及可能直達系統｜**對應資產**：A1~A6

### 看什麼

- MyBatis `${}`：追變數來源，**來自 request 且未白名單**才是 finding
- 動態排序 / 動態表名欄名：是否白名單
- 命令注入、路徑穿越（特別是 `upload-service`）
- 檔案上傳：副檔名、MIME、大小、存放位置、是否可被當成程式執行
- 反序列化（Jackson / fastjson / 原生序列化）
- SSRF：由請求控制的對外連線目標
- ES query 拼接

### 怎麼判

**可控性**是關鍵：輸入能不能被外部影響。來自 enum、常數、內部固定值 → 誤報。

---

## 軸 5 ｜ 機密與設定暴露

**踩破的邊界**：跨多條｜**對應資產**：A6、A4

### 看什麼

- 硬編的 API Key、密碼、Token、私鑰（含測試檔、註解、範例設定）
- 設定檔中的明文憑證，以及哪些設定檔進了版控
- Log 是否印出密碼、Token、完整 API Key、第三方回調原始 body 的敏感欄位
- 錯誤回應是否洩漏 stack trace、SQL、內部路徑
- Actuator / Swagger / 文件端點是否對外暴露
- CORS 設定是否過寬
- CI 設定（`Jenkinsfile`）中的憑證處理

### 報告紀律

**找到機密時，finding 要寫、值不要寫**（`rules/scope-safety.md` 紅線 3）。

### 誤報注意

log 印物件時，`toString()` 可能已排除敏感欄位（Lombok `@ToString.Exclude` 或自訂）。要去讀那個類別。

---

## 軸 6 ｜ 第三方回調與對接

**踩破的邊界**：5｜**對應資產**：A1、A3

### 看什麼

- 每個回調入口的驗簽方式：有沒有驗、驗什麼、簽章涵蓋哪些欄位（**金額有沒有被簽進去**）
- IP 白名單是否存在，以及在哪一層執行（應用層的白名單在 nginx 之後可能形同虛設）
- 防重放：timestamp + nonce + 時間窗
- 回調的冪等：同一筆通知重送會不會重複入帳
- 驗簽失敗時的行為：是擋下還是只記 log
- 各回調入口的驗簽是不是各寫各的（不一致 = 總有一個漏）

### 怎麼判

把回調當成**外部可完全控制的輸入**。唯一能信的是簽章驗證過的欄位。

---

## 軸 7 ｜ 依賴與已知漏洞

**踩破的邊界**：視 CVE 而定｜**對應資產**：全部

### 看什麼

- 直接依賴與傳遞依賴的版本（`pom.xml`、`mvn dependency:tree` 若可跑）
- 已知高風險元件的版本
- 有沒有在用已被棄用的不安全 API

### 怎麼判（這條最容易誤報）

**CVE 存在 ≠ 這個專案受影響。** 必須確認三件事才算 finding：

1. 該依賴**確實在編譯或執行期被使用**（不是只在 test scope、不是被排除）
2. **受影響的類別／功能有被實際呼叫**
3. 觸發條件在本專案的用法下**成立**

三者缺一 → 降為「待查」或「版本老舊」的資訊性項目，不給高嚴重度。

### 邊界

**升級不是本範本的職責。** 只標「目前版本、風險、建議目標版本、相容風險」，
實際升級走 `prompt-setup 版本管理`。
