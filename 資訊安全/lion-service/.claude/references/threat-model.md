# 包網平台威脅模型

> 掃描前先看這份。**知道誰會攻擊、想拿什麼，才知道該往哪裡看。**
> 不看這份就開始 grep，會掃出一堆技術上正確但業務上無關痛癢的東西。

---

## 1. 包網（白標）這個業務型態的特殊性

一套系統同時服務**多家包網商**，每家有自己的玩家、自己的帳務、自己的後台。
彼此是**商業競爭對手**。

這件事推導出本平台最特別的一條風險：

> **A 包網商能看到 B 包網商的任何東西，就是事故。**
> 不只是資料外洩 —— 是把客戶的營運機密洩漏給他的競爭對手。

而且這條風險有一個很糟的性質：**在單一包網商的測試環境裡，100% 測不出來。**
功能全部正常，測試全過，上線後才爆。

---

## 2. 要保護的資產（依價值排序）

| # | 資產 | 失守的後果 |
|---|---|---|
| A1 | **玩家餘額與金流** | 直接資金損失，不可逆 |
| A2 | **包網商之間的資料邊界** | 商業機密外洩給競爭對手，客戶流失 + 可能的法律責任 |
| A3 | **注單與派彩結果** | 可竄改 = 平台可被提款，且難以事後察覺 |
| A4 | **玩家個資**（帳號、手機、金流紀錄） | 法遵事故 |
| A5 | **後台管理權限** | 拿到就等於拿到上面全部 |
| A6 | **第三方對接憑證** | 可冒充平台對第三方操作 |
| A7 | **系統可用性** | 營收中斷（但本範本為靜態稽核，不做 DoS 驗證） |

## 3. 攻擊者模型

| 攻擊者 | 已有什麼 | 想要什麼 | 最可能的路徑 |
|---|---|---|---|
| **惡意玩家** | 一個合法玩家帳號 | 加錢、改注單、看別人資料 | 改請求參數（金額、orderNo、userId）、重放、併發打時序 |
| **惡意包網商** | 一組合法的包網商後台帳號 | 看競爭對手的營運數據 | **改 `platformId`**、猜連號、用共用查詢介面撈跨平台資料 |
| **惡意代理** | 代理後台帳號 | 看上層 / 平行代理的資料、改自己的抽成 | 沿 `agentId` 層級往上或往旁越權 |
| **被入侵的第三方遊戲商** | 合法的回調憑證或 IP | 偽造注單、偽造派彩 | 回調重放、簽章繞過、金額竄改 |
| **外部未認證攻擊者** | 什麼都沒有 | 任何立足點 | 未授權入口、上傳、注入、已知 CVE |
| **內部人員** | 後台帳號或程式碼存取 | —— | 本範本**不做內部威脅建模**，但會報「操作無稽核軌跡」這類使能條件 |

> **最需要優先看的是「惡意包網商」。** 它有合法憑證、有動機、且它要拿的東西（A2）
> 正好是這個業務型態獨有的資產。一般的資安檢查清單不會涵蓋它。

## 4. 信任邊界（finding 幾乎都發生在這些線上）

```
外部未認證
    │  ← 邊界 1：認證（誰進得來）
已登入的人（玩家 / 包網商 / 代理 / 後台人員）
    │  ← 邊界 2：授權（能做什麼）
可執行的動作
    │  ← 邊界 3：資料範圍（platformId / agentId 能看到誰的資料）  ★包網核心
該看得到的資料
    │  ← 邊界 4：金額與狀態（能改成什麼）
實際入帳 / 實際結算
```

另有兩條旁路：

```
第三方遊戲商 ──→ 回調入口 ── 邊界 5：來源可信嗎（驗簽 / IP / 重放）
內部服務   ──→ 內部介面 ── 邊界 6：內部真的是內部嗎（nginx 之後還算不算）
```

**每一條 finding 都應該指得出它踩破的是哪一條邊界。** 指不出來，多半是個程式碼品質問題而不是漏洞。

## 5. 這個技術棧本身帶來的風險面

| 事實 | 帶來什麼 |
|---|---|
| **Spring Boot 2.0.2.RELEASE（2018）** | 早已停止維護，累積大量已知 CVE；Spring Security 的預設值與現代版本差異大 |
| **Java 8** | 同上；且部分現代防護機制不可用 |
| **MyBatis XML** | `${}` 字串替換是注入面（但多數是欄名／排序，需逐一判斷） |
| **ShardingSphere 分片** | 實際下到 DB 的 SQL 與 XML 寫的不同，注入與隔離都要考慮改寫後的樣子 |
| **多套後台前端**（admin / agent / third / bet-station / boss / manage / bet-order） | 授權面很寬，且各後台的權限模型可能不一致 |
| **多個第三方回調入口** | 每個都是一條外部可達路徑，驗簽方式可能各寫各的 |
| **Elasticsearch 6.8 + 7.17 並用** | 兩套 client、兩種行為，容易有一邊漏了防護 |

> **依賴版本舊 ≠ 一定有漏洞。** CVE 要確認「受影響的元件是否實際被使用」才算數
> （`rules/false-positive.md` §2）。升級本身屬 `prompt-setup 版本管理` 的職責，本範本只評級與回報。

## 6. 已知事故：filter 繞過（**每次掃描優先檢查**）

> 這不是假設，是**已經發生過**的。掃描時這一類優先於其他所有推測性的風險。

### 事故摘要

| 項目 | 內容 |
|---|---|
| **發生了什麼** | 認證 filter 存在繞過漏洞，攻擊者藉此進入系統 |
| **成因** | **帶特定副檔名的請求被直接放行，完全不做檢查** |
| **回報來源** | 團隊內部回報（口述：「filter 有漏洞」「被打進來」「有加 `.do` 的都不檢查」） |

### 為什麼這一類特別危險

1. **它偽裝成「有防線」。** filter 確實存在、確實在檢查登入 ——
   所以任何「看到上游有 filter 就判誤報」的稽核紀律，都會直接放過它。
   本範本為此在 `rules/false-positive.md` §2.5 與 `agents/finding-verifier.md`
   加了強制的「防線有效性三問」。
2. **副檔名是請求方完全可控的字串**，不是資源類型的證明。
   以它當放行依據，等於讓攻擊者自己決定要不要被檢查。
3. **一破全破。** 認證是邊界 1，它被繞過之後，後面所有依賴「已登入」前提的
   授權、隔離、金流檢查，前提全部不成立。

### 掃描時的固定動作

| 動作 | 由誰 |
|---|---|
| 逐一列出每個 filter 的**提早放行分支**，產出人工審查用的盤點表 | `filter-bypass-auditor` |
| 檢查路徑比對方式（精確比對 vs 子字串比對、有無正規化） | 同上 |
| 判「上游 filter 擋掉了 → 誤報」之前，強制過三問 | `finding-verifier` |

> **即使某個分支判不出可不可達，也要列進盤點表並標「待人工確認」。**
> 盤點表的價值在完整 —— 它能直接當清單交給熟悉該模組的工程師逐條審。

### 修復方向的通則（具體改法仍以實際程式碼為準）

- 放行清單改為**明確列舉的路徑**，用精確比對，不用副檔名、不用子字串比對。
- 比對前先正規化路徑，並確認與容器分派所用的字串一致。
- 檢查失敗一律 `return`，不得只記 log。
- 能移除的放行分支就移除 —— 多數是早年為一次性需求加的。
