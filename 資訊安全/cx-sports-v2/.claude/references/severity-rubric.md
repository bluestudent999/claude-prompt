# 嚴重度與信心分級

> 嚴重度是給**決策者排優先序**用的，不是給稽核者展示功力用的。
> 全部標成 CRITICAL 等於沒有分級。

---

## 1. 嚴重度（依「對本業務的實際損害」定，不是照 CVSS 抄）

| 級別 | 判準 | 本平台的典型例子 |
|---|---|---|
| **CRITICAL** | 直接造成不可逆資金損失，或跨平台商資料邊界失守，或未認證即可取得系統控制權 | 可改餘額／可竄改派彩金額／A 平台商讀得到 B 家注單／未認證 RCE |
| **HIGH** | 需要一個低門檻前提（有任一合法帳號），即可越權存取他人資料或影響帳務 | 物件級越權讀他人注單／回調可偽造但金額受限／後台功能級權限缺失 |
| **MEDIUM** | 需要較高前提，或影響限於單一使用者，或需搭配其他問題才成事 | 自身資料的 XSS／可列舉他人存在但看不到內容／錯誤訊息洩漏內部路徑 |
| **LOW** | 資訊性、深度防禦不足，短期無實際可利用路徑 | 缺 security header／版本號外洩／log 過度詳細但無敏感資料 |

### 多平台情境的加權（本平台特有，優先於上表）

| 情況 | 調整 |
|---|---|
| **跨 `platformId` 邊界失守** | 一律 **CRITICAL**，即使只是唯讀 —— 那是把客戶的營運機密給了他的競爭對手 |
| **在單平台測試環境測不出來的問題** | **升一級**。它不會被既有測試攔到，會一路上線 |
| **影響實際入帳金額** | 最低 **HIGH**，不論金額大小 —— 可重複執行的小額就是大額 |
| **有對帳／風控／人工審核可攔截** | **降一級**，並在 finding 寫明是靠什麼攔的（那條防線也可能失效） |

## 2. 信心（與嚴重度分開標）

| 級別 | 意思 | 可否進 Finding |
|---|---|---|
| **高** | 攻擊路徑完整追過、上游確認無防護、影響明確 | ✅ |
| **中** | 路徑合理但有一段靠推論（例如未能確認某 Filter 實際套用範圍） | ✅，但要在 finding 寫明哪一段是推論 |
| **低** | 有疑慮但關鍵環節未驗證 | ❌ 放「待查清單」，不給嚴重度 |

> **「CRITICAL／信心低」是自相矛盾的東西。** 真的那麼嚴重，就把它驗清楚再報。

---

## 3. 修復成本（排優先序用，與嚴重度一起看）

| 級別 | 意思 |
|---|---|
| **低** | 單點修改，不動介面與資料結構（加一行檢查、改一個設定） |
| **中** | 動到一個模組內部，需要測試但不影響呼叫方 |
| **高** | 跨模組、動介面或資料結構、需要協調其他 repo 或第三方 |

### 優先序矩陣（`rules/report-standard.md` §4）

| | 修復成本低 | 修復成本高 |
|---|---|---|
| **嚴重度高** | **立即修** | **排程修**（開票、拆任務） |
| **嚴重度低** | **順手修**（併進下次相關改動） | **評估後決定**（要寫清楚不修的風險，讓人能明確簽下接受） |

## 4. 與 cx-sports-v2 自己的分級對照

`cx-sports-v2` 有 `cx-sports-v2/.claude/rules/severity-rubric.md`（開發期 review 用）。

- **兩套不衝突**：那套判「這個 diff 能不能合」，這套判「這個漏洞多急著修」。
- 報告中若引用 cx-sports-v2 的規範條文當依據，**用它的用語**，讓維護方一眼認得出是自家規則。
- 兩套判定不一致時，報告採本檔的分級，並在 finding 註明差異與理由。
