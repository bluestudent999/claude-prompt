# cx-sports-v2 威脅模型

> 掃描前先看這份。**知道誰會攻擊、想拿什麼，才知道該往哪裡看。**
> 不看這份就開始 grep，會掃出一堆技術上正確但業務上無關痛癢的東西。

---

## 1. 這個系統的兩個業務特性

### 特性一：體育投注

錢的流向由**外部真實世界的賽事結果**決定，而不是由系統自己產生的隨機數。
這帶來一類其他博彩系統沒有的風險：**資訊不對稱攻擊** ——
攻擊者不需要入侵系統，只要比系統早知道結果、或讓系統晚知道結果，就能穩定獲利。

### 特性二：多平台（包網）

`platformId` 約 8,700 處引用，一套系統服務多個平台，彼此是商業競爭對手。

> **A 平台能看到 B 平台的任何東西，就是事故。**

這條風險有個很糟的性質：**在單一平台的測試環境裡 100% 測不出來。**
功能全過、測試全綠，上線才爆。

而這個 repo 還多一層：**CI 不跑測試**（`Jenkinsfile` 用 `-Dmaven.test.skip=true`），
所以任何「靠測試會攔下來」的假設都不成立，防線只剩 code review 與執行期。

## 2. 要保護的資產（依價值排序）

| # | 資產 | 失守的後果 |
|---|---|---|
| A1 | **玩家餘額與金流** | 直接資金損失，不可逆 |
| A2 | **賠率與限額設定** | 改得動賠率或繞得過限額 = 平台曝險失控，單一事件即可被提款 |
| A3 | **賽事結果與結算** | 改得動結果 = 可任意決定誰贏。難以事後察覺 |
| A4 | **平台之間的資料邊界** | 商業機密外洩給競爭對手 |
| A5 | **注單**（建立時間、賠率、狀態） | 事後改注單 = 穩贏 |
| A6 | **總控制中心權限**（跨平台） | 權限最大的後台，拿到就等於拿到上面全部 |
| A7 | 玩家個資 | 法遵事故 |
| A8 | 第三方對接憑證（資料源、錢包、支付） | 可冒充平台對外操作 |

> **A2 與 A3 是體育投注獨有的。** 一般的資安檢查清單不會涵蓋它們，
> 但它們的損失規模可以遠大於單一帳號被盜。

## 3. 攻擊者模型

| 攻擊者 | 已有什麼 | 想要什麼 | 最可能的路徑 |
|---|---|---|---|
| **職業投注者 / 套利者** | 合法帳號、**比系統快的賽事資訊** | 用已知結果下注 | **延遲下注**（賽事已有結果但系統還沒關盤）、搶賠率變動的時間窗、繞過限額放大單注 |
| **惡意玩家** | 合法帳號 | 加錢、改注單、看別人資料 | 改請求參數（金額、賠率、注單號）、重放、併發打時序 |
| **惡意平台商** | 合法的平台後台帳號 | 看競爭對手營運數據 | **改 `platformId`**、猜連號、用跨平台查詢介面撈資料 |
| **惡意代理** | 代理後台帳號 | 看上層 / 平行代理的資料、改抽成 | 沿 `agentId` 層級越權 |
| **被入侵的第三方**（資料源 / 錢包 / 支付） | 合法憑證或 IP | 偽造賽果、偽造注單、偽造入帳 | 回調重放、驗簽繞過、MQ 資料污染 |
| **外部未認證攻擊者** | 什麼都沒有 | 任何立足點 | **filter 繞過**（見 §6，已發生過）、未授權入口、注入、已知 CVE |

> **最需要優先看的是「職業投注者」與「外部未認證攻擊者」。**
> 前者的攻擊面（A2、A3、A5）是體育投注獨有、一般清單查不到；
> 後者已經實際成功過（§6）。

## 4. 信任邊界

```
外部未認證
    │  ← 邊界 1：認證（誰進得來）        ★ §6 已被繞過過
已登入的人（玩家 / 平台商 / 代理 / 後台人員）
    │  ← 邊界 2：授權（能做什麼）
可執行的動作
    │  ← 邊界 3：資料範圍（platformId / agentId 能看到誰的）
該看得到的資料
    │  ← 邊界 4：金額、賠率、限額、注單狀態（能改成什麼）
實際入帳 / 實際結算
```

旁路：

```
第三方資料源 ──→ MQ / 回調 ── 邊界 5：賽果與賠率來源可信嗎
第三方錢包   ──→ 回調       ── 邊界 6：驗簽 / IP / 重放
內部服務     ──→ 內部介面   ── 邊界 7：nginx 之後還算不算內部
```

**每條 finding 都應該指得出它踩破的是哪一條邊界。**

## 5. 這個技術棧與結構帶來的風險面

| 事實 | 帶來什麼 |
|---|---|
| **Spring Boot 2.7.11**（OSS 支援已終止） | 累積 CVE；但比 2.x 早期版本好，判 CVE 時要看實際版本不要照抄舊清單 |
| **20+ 個 filter／攔截器**（app-service 就有 10 個以上） | 每個都有自己的白名單與比對邏輯，**只要一套寫鬆就破**（§6） |
| **多組驗簽 filter**（`SignFilter` / `QuickSignFilter` / `PlatformSignFilter` / `ThirdFilter` / `CgThirdFilter` / `XjCollectorFilter` / `SingleWalletSignFilter`） | 各寫各的簽章邏輯，涵蓋欄位與時間窗可能不一致 |
| **輸入過濾集中在 filter**（`SqlInjectAndXssFilter`、`CheckSQLInjectionFilter`、`XssFilter`） | 這類「集中式黑名單過濾」本身就是繞過的主要目標 |
| **monorepo，7 個前端在同 repo** | 前端原始碼會被一起掃到（硬編機密、內部 URL） |
| **ShardingSphere 分片** | 實際下到 DB 的 SQL 與 XML 不同，注入與隔離都要考慮改寫後的樣子 |
| **ES 6.8 + 7.17 並用**（含主從切換 aspect） | 兩套 client、兩種行為，容易一邊漏防護 |
| **Kafka 走 Spring Cloud Stream** | 訊息來源的信任邊界（賽果 / 賠率若由 MQ 進來，那是邊界 5） |
| **CI 不跑測試** | 「測試會攔住」的假設一律不成立 |
| **`platformId` 拼寫不一致**（`platFormId` / `platform_Id` / `platformid`） | grep 不分大小寫，否則會漏掉隔離檢查的死角 |

## 6. 已知事故：filter 繞過（**每次掃描優先檢查**）

> 這不是假設，是**已經發生過**的。掃描時這一類優先於其他所有推測性風險。

### 事故摘要

| 項目 | 內容 |
|---|---|
| **發生了什麼** | 認證 filter 存在繞過漏洞，攻擊者藉此進入系統 |
| **成因** | **帶特定副檔名的請求被直接放行，完全不做檢查** |
| **回報來源** | 團隊內部回報（口述：「filter 有漏洞」「被打進來」「有加 `.do` 的都不檢查」） |

### 本 repo 已觀察到的同類寫法（**掃描起手點，非結論**）

建立本範本時讀程式碼所見，**尚未驗證可達性與上游防線**，列為必查：

| 位置 | 寫法 |
|---|---|
| `cx-sport-app-service/.../filter/MyFilter.java:190` | `if (uri.contains(".do")) { filterChain.doFilter(...); return; }` —— **`contains`，比 `endsWith` 更寬** |
| `cx-sport-app-service/.../filter/MyFilter.java:194` | `if (uri.endsWith(".svg")) { ... return; }` |
| `cx-sport-app-service/.../filter/MyFilter.java:268` | `isWhiteUri = ... \|\| uri.endsWith(".json")` |
| `manage-center/.../filter/MyFilter.java:86` | `isWhiteUri = ... \|\| uri.endsWith(".json")` —— **總控制中心，權限最大的後台** |
| `manage-center/.../filter/MyFilter.java:80-82` | `getServletPath()` 取不到時 fallback 到 `getRequestURI()` —— 兩者語意不同，混用是比對縫隙 |
| `lib/sport-framework/.../CheckSQLInjectionFilter.java:58` | `str.endsWith("*") && requestPath.startsWith(...)` —— 前綴比對 |
| `cx-sport-app-service/.../flowcontrol/IpAccessFlowControl.java:98` | IP 白名單用 `startsWith` 前綴比對（`1.2.3.4*` 會命中 `1.2.3.40`） |

> **這些是待查清單，不是 finding。** 每一條都要照 `references/scan-axes.md` 軸 8 的流程
> 追可達性、確認上游有無防線、確認業務上是否必要，才能定性。
> `filter-bypass-auditor` 的第一件事就是把這張表補完並逐條定性。

### 為什麼這一類特別危險

1. **它偽裝成「有防線」。** filter 確實存在、確實在檢查登入 ——
   所以任何「看到上游有 filter 就判誤報」的稽核紀律，都會直接放過它。
   本範本為此在 `rules/false-positive.md` §2.5 與 `agents/finding-verifier.md`
   加了強制的「防線有效性三問」。
2. **副檔名是請求方完全可控的字串**，不是資源類型的證明。
3. **一破全破。** 認證是邊界 1，被繞過之後，後面所有依賴「已登入」前提的
   授權、隔離、金流、限額檢查，前提全部不成立。

### 修復方向的通則（具體改法仍以實際程式碼為準）

- 放行清單改為**明確列舉的路徑**，用精確比對，不用副檔名、不用子字串比對。
- 比對前先正規化路徑，並確認與容器分派所用的字串一致（`getServletPath` / `getRequestURI` 擇一並貫徹）。
- 檢查失敗一律 `return`，不得只記 log。
- 能移除的放行分支就移除 —— 多數是早年為一次性需求加的（如註解寫「聊天室對接」的那條）。
