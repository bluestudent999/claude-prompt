# 九條掃描軸

> 每條軸寫的是「**看什麼、怎麼判、什麼情況是誤報**」，不是完整的檢查清單。
> 實際的判準以標的自己的 `cx-sports-v2/.claude/rules/security.md`、`patterns.md`、`checks/` 為準 ——
> 「你們自己的規則在這裡沒被遵守」是接受度最高的 finding。

---

## 軸 1 ｜ 多平台隔離（最高優先）

**踩破的邊界**：3（資料範圍）｜**對應資產**：A2

### 看什麼

- `platformId` 的**來源**：從 session／token 取，還是從 request body／query 取？
- 有沒有統一的取得管道（Context、AOP、攔截器），還是各寫各的？
- 查詢條件裡的 `platformId` 會不會被請求覆寫？
- 跨平台的共用查詢介面（報表、統計、匯出）有沒有限制範圍？
- 快取的 key 有沒有帶 `platformId`（沒帶 = 跨平台污染）？
- ES 索引、MQ topic、檔案路徑有沒有按平台分隔？

### 怎麼判

**判準只有一句：請求方能不能影響「查到誰的資料」。**
能 → finding。不能（被 session 覆寫、被 AOP 強制）→ 誤報。

### 最容易誤報的地方

`platformId` 在下層 Service 看起來沒檢查，但**上層或 AOP 已經覆寫**。
一定要往上追到對外入口才能下結論。

## 軸 2 ｜ 認證、授權與越權

**踩破的邊界**：1、2、3｜**對應資產**：A5、A3、A4

### 看什麼

- 對外入口是否都落在認證規則內（注意：規則可能在 `SecurityConfig` 路徑比對、Filter、或 nginx，不在註解上）
- 功能級授權：角色能不能做這個動作
- **物件級授權**：能不能操作「不屬於自己的那一筆」（改 orderNo / userId 就拿到別人的）
- **代理層級越權**：沿 `agentId` 往上層或平行代理看資料
- 多套後台的權限模型是否一致（admin / agent / ctrl-center / boss-crtl-center / manage / boss / mts）
- 內部介面的「內部」怎麼認定 —— nginx 之後還算不算內部？

### 怎麼判

物件級授權是最常漏的：**功能有權限、但沒檢查這筆資料是不是你的**。
判準：把請求裡的識別碼換成別人的，會不會成功？

---

## 軸 3 ｜ 金流與錢包

**踩破的邊界**：4｜**對應資產**：A1、A3

### 看什麼

- 金額是否可由請求方影響（前端傳金額 = 高風險）
- 餘額異動是否照「驗餘額 → 鎖行 → 扣減 → 寫流水」的順序，有無跳步
- 悲觀鎖 / 分散式鎖的覆蓋範圍，鎖的粒度對不對
- **冪等**：重複請求、重放、併發同時打會怎樣
- 負數、極大值、精度截斷（`BigDecimal` vs `double`、`RoundingMode`）
- 退款 / 撤單 / 補單路徑的權限與重複執行
- 派彩與結算的金額來源是否可竄改

### 怎麼判

參照 `cx-sports-v2/.claude/rules/security.md` 的金額章節與 `cx-sports-v2/.claude/checks/bigdecimal-rounding.md`、
`cx-sports-v2/.claude/checks/idempotency-orderno.md` —— 違反它自己訂的規則就是 finding。

### 誤報注意

規範允許純統計（筆數、頁數、耗時）用 `double`。要確認那個值會不會變成實際入帳金額。

---

## 軸 4 ｜ 注入與輸入處理

**踩破的邊界**：4、以及可能直達系統｜**對應資產**：A1~A6

### 看什麼

- MyBatis `${}`：追變數來源，**來自 request 且未白名單**才是 finding
- 動態排序 / 動態表名欄名：是否白名單
- 命令注入、路徑穿越（特別是 `cx-sport-app-service`）
- 檔案上傳：副檔名、MIME、大小、存放位置、是否可被當成程式執行
- 反序列化（Jackson / fastjson / 原生序列化）
- SSRF：由請求控制的對外連線目標
- ES query 拼接

### 怎麼判

**可控性**是關鍵：輸入能不能被外部影響。來自 enum、常數、內部固定值 → 誤報。

---

## 軸 5 ｜ 機密與設定暴露

**踩破的邊界**：跨多條｜**對應資產**：A6、A4

### 看什麼

- 硬編的 API Key、密碼、Token、私鑰（含測試檔、註解、範例設定）
- 設定檔中的明文憑證，以及哪些設定檔進了版控
- Log 是否印出密碼、Token、完整 API Key、第三方回調原始 body 的敏感欄位
- 錯誤回應是否洩漏 stack trace、SQL、內部路徑
- Actuator / Swagger / 文件端點是否對外暴露
- CORS 設定是否過寬
- CI 設定（`Jenkinsfile`）中的憑證處理

### 報告紀律

**找到機密時，finding 要寫、值不要寫**（`rules/scope-safety.md` 紅線 3）。

### 誤報注意

log 印物件時，`toString()` 可能已排除敏感欄位（Lombok `@ToString.Exclude` 或自訂）。要去讀那個類別。

---

## 軸 6 ｜ 第三方回調與對接

**踩破的邊界**：5｜**對應資產**：A1、A3

### 看什麼

- 每個回調入口的驗簽方式：有沒有驗、驗什麼、簽章涵蓋哪些欄位（**金額有沒有被簽進去**）
- IP 白名單是否存在，以及在哪一層執行（應用層的白名單在 nginx 之後可能形同虛設）
- 防重放：timestamp + nonce + 時間窗
- 回調的冪等：同一筆通知重送會不會重複入帳
- 驗簽失敗時的行為：是擋下還是只記 log
- 各回調入口的驗簽是不是各寫各的（不一致 = 總有一個漏）

### 怎麼判

把回調當成**外部可完全控制的輸入**。唯一能信的是簽章驗證過的欄位。

---

## 軸 7 ｜ 依賴與已知漏洞

**踩破的邊界**：視 CVE 而定｜**對應資產**：全部

### 看什麼

- 直接依賴與傳遞依賴的版本（`pom.xml`、`mvn dependency:tree` 若可跑）
- 已知高風險元件的版本
- 有沒有在用已被棄用的不安全 API

### 怎麼判（這條最容易誤報）

**CVE 存在 ≠ 這個專案受影響。** 必須確認三件事才算 finding：

1. 該依賴**確實在編譯或執行期被使用**（不是只在 test scope、不是被排除）
2. **受影響的類別／功能有被實際呼叫**
3. 觸發條件在本專案的用法下**成立**

三者缺一 → 降為「待查」或「版本老舊」的資訊性項目，不給高嚴重度。

### 邊界

**升級不是本範本的職責。** 只標「目前版本、風險、建議目標版本、相容風險」，
實際升級走 `prompt-setup 版本管理`。

## 軸 8 ｜ 過濾器與路徑比對繞過（優先序：**最高**）

**踩破的邊界**：1、2｜**對應資產**：全部｜**狀態**：**此平台已發生過實際事故**

> **這條軸不是理論風險。** 已知事故：filter 存在漏洞而被打進來，成因是
> **帶特定副檔名的請求被直接放行、不做檢查**。
> **而且本 repo 已觀察到多處同類寫法**（`MyFilter` 的 `.do` / `.svg` / `.json` 分支、
> `CheckSQLInjectionFilter` 與 IP 白名單的前綴比對）—— 清單見 `references/threat-model.md` §6，
> `filter-bypass-auditor` 的第一件事就是把那張表補完並逐條定性。
>
> 本 repo 有 **20+ 個 filter／攔截器**，其中 app-service 一個模組就有 10 個以上。
> 每個都有自己的白名單與比對邏輯，**只要一套寫鬆就破** —— 所以要逐個讀，不能抽樣。

### 為什麼要獨立成一條軸

其他軸問的是「這個入口有沒有防線」。這條軸問的是**完全相反的一句**：

> **那道防線，真的擋得住嗎？**

一個 filter「存在」而且「看起來在檢查登入」，不代表每個請求都會走到那段檢查。
**繞過幾乎都發生在檢查之前** —— 在某個提早 return 的分支裡。

### 看什麼

#### 1. 提早放行的分支（最高優先）

filter 開頭常有一段「這些不用檢查」的白名單，通常長這樣：

```java
if (<某條件>) { chain.doFilter(request, response); return; }   // 檢查都還沒開始
```

**逐一列出每個這種分支**，對每一個問三件事：

| 問題 | 為什麼 |
|---|---|
| 放行條件是什麼？ | 條件寫錯 = 整個認證形同虛設 |
| 攻擊者能不能**自己構造出符合這個條件的請求**去打受保護的路徑？ | 這就是繞過 |
| 這個放行在業務上**真的必要**嗎？ | 很多是早年為了某個一次性需求加的，早就不需要了 |

> **最危險的是「依副檔名放行」**（`.do`、`.js`、`.css`、`.jpg`…）。
> 副檔名是**請求方完全可控的字串**，不是資源類型的證明。
> 用它當放行依據，等於讓攻擊者自己決定要不要被檢查。

#### 2. 路徑比對方式

| 寫法 | 問題 |
|---|---|
| `startsWith` / `endsWith` / `contains` / `indexOf` | 子字串比對，不是路徑比對。`/api/publicX/admin` 會命中 `/api/public` |
| 大小寫敏感度不一致 | filter 比 `/admin`，容器可能把 `/Admin` 導到同一個 servlet |
| 未正規化就比對 | `//admin`、`/./admin`、`/a/../admin`、尾斜線、URL 編碼的 `%2e` |
| `getRequestURI()` vs `getServletPath()` vs `getPathInfo()` | 三者語意不同（含不含 context path、有沒有解碼）。filter 用 A 比對、容器用 B 分派 = 縫 |
| `;` 參數 | `/admin;x=1` 在某些容器下仍路由到 `/admin` |

**判準**：**filter 看到的字串，和容器實際拿來分派的字串，是不是同一個？** 不是 → 那個差異就是繞過空間。

#### 3. filter 本身的套用範圍

- 註冊的 URL pattern 有沒有涵蓋所有受保護路徑
- **dispatcher type**：FORWARD / INCLUDE / ASYNC 預設不經過 filter
- **filter 順序**：認證 filter 是否排在所有會做事的 filter 之前
- 多個 filter 各有一套白名單 → 只要一套寫鬆就破
- Spring Security 的 `antMatchers` 與自訂 filter 的比對規則**不一致**時，以寬的那個為準

#### 4. 判定失敗後有沒有真的擋住

```java
if (!valid) { log.warn("..."); }      // 沒有 return，繼續往下走
chain.doFilter(request, response);
```

驗證失敗只記 log 不中斷，是這類程式碼很常見的寫法。

### 怎麼判

**不要只看 filter 有沒有做認證，要看「有哪些請求走不到那段認證」。**

作法：把 filter 從上往下讀，每遇到一個 `return` 或 `chain.doFilter`，
記下「走到這裡就不會被檢查了」，再問這個條件能不能被構造出來。

### 報告紀律

依 `rules/scope-safety.md` 紅線 3：**寫清楚是哪一個分支、什麼比對方式、怎麼修**，
**不要附上可直接使用的繞過請求**。修復方需要知道的是「哪一行寫錯」，不是「怎麼打進來」。

### 誤報注意

- 放行的若是**真正的靜態資源目錄**（由容器另行處理、不進業務邏輯），且路徑比對嚴謹 → 不是 finding。
- nginx 或閘道若已在上游做了同樣的過濾且比對更嚴格 → 降嚴重度，但**要指出是哪一層擋的**；
  應用層自己的防線仍然寫鬆，屬深度防禦不足。

## 軸 9 ｜ 賠率、限額與結算（體育投注獨有）

**踩破的邊界**：4、5｜**對應資產**：A2、A3、A5

> 這條軸是**體育投注獨有**的，一般資安檢查清單不會涵蓋。
> 它的損失規模可以遠大於單一帳號被盜 —— 因為攻擊者不需要入侵系統，
> 只要**比系統早知道結果、或讓系統晚知道結果**，就能穩定獲利。

### 看什麼

#### 1. 賠率的可信來源

- 下注請求裡**有沒有帶賠率**？後端有沒有以自己的當下賠率重新驗證？
  > 前端傳賠率、後端照收 = 玩家自己決定賠率。
- 賠率變動與下注之間的**時間窗**怎麼處理：接受舊賠率嗎？容忍多久？
- 賠率來源（第三方資料源 / MQ）的信任邊界在哪，有沒有驗簽或合理性檢查。

#### 2. 限額（單注 / 單場 / 單日 / 玩家層級 / 平台層級）

- 限額檢查在哪一層？**併發下多筆能不能一起突破**（各自檢查時都還沒超過）？
- 串關（parlay）的限額怎麼算，會不會被拆單繞過？
- 限額設定本身誰能改，改了有沒有稽核軌跡（屬 A2，權限等同改賠率）。

#### 3. 延遲下注（late betting）

**這是體育投注最典型的攻擊。** 賽事已經有結果，但系統還沒關盤或還沒收到結果，
攻擊者用已知結果下注。

- **關盤時機**由誰決定、以哪個時間為準（伺服器時間？資料源時間？）
- 走地／滾球盤的**接單延遲**與結果回傳延遲，中間的時間差有多大
- 賽果進來之後，**還接不接受該場的注單**？有沒有以賽果時間回溯檢查？

#### 4. 結算與賽果

- 賽果的來源與可信度；**人工改賽果**的權限與稽核軌跡
- 重新結算（re-settlement）路徑：誰能觸發、能不能重複執行、金額怎麼沖正
- 結算金額的計算來源是否可竄改
- 取消／作廢注單（void）的權限與時機

#### 5. 注單本身

- 注單建立後，**賠率、金額、賽事、狀態**是否還可被修改
- 撤單（cancel）的時間窗與權限
- 注單號可否預測或列舉

### 怎麼判

**判準：玩家能不能影響「以什麼條件成立這一注」。**
賠率、限額、關盤時機、賽果 —— 任何一項可被請求方影響或可被搶時間窗，就是候選 finding。

### 誤報注意

- 賠率若在後端以 `platformId` + 賽事 + 盤口重查後才計算，前端帶的只是顯示用 → 不是 finding。
  **要追到實際計算派彩的那一行**，看它用的是哪個賠率。
- 限額檢查若在 DB 層有唯一約束或悲觀鎖保護 → 併發突破可能不成立，要確認鎖的範圍。
