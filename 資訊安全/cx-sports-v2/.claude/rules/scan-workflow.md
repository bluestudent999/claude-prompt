# 掃描流程

> 四個階段，**不得跳步**。最常見的失敗是跳過階段 1 直接開始 grep ——
> 沒有攻擊面地圖就掃，結果是「grep 到什麼就報什麼」，而不是「照風險排序地看」。

---

## 階段 1 ｜ 盤點攻擊面（recon）

由 `recon` agent 執行，產出 `sec-reports/<日期>/recon.md`。

| 要盤出來的 | 為什麼要先知道 |
|---|---|
| **對外入口清單** | 沒有入口清單，就無法論證任何 finding 的可達性 |
| **認證與授權機制在哪** | 決定後面每條 finding 要往哪裡追上游防線 |
| **多平台隔離怎麼實作的** | `platformId` 是從 session 來、request 來、還是 AOP 覆寫？這決定整條隔離軸的掃法 |
| **金流路徑** | 哪些地方會實際異動餘額 |
| **第三方回調入口與驗簽機制** | 那些回調各自怎麼驗 |
| **機密存放位置** | 設定檔、DB config 表、環境變數 |
| **依賴清單與版本** | CVE 軸的輸入 |

**階段 1 沒做完，不准進階段 2。**

---

## 階段 2 ｜ 分軸掃描（可平行）

九條軸見 `references/scan-axes.md`，對應六個 auditor：

| 軸 | Agent |
|---|---|
| 多平台隔離 | `tenant-isolation-auditor` |
| 認證授權與越權 | `authz-auditor` |
| 金流與錢包 | `money-flow-auditor` |
| 注入與輸入處理 | `injection-auditor` |
| 機密與設定暴露 | `config-exposure-auditor` |
| 依賴 CVE | `dependency-cve-auditor` |

**紀律：**

- 每個 auditor **只掃自己那條軸**；看到別軸的問題記一筆丟給對應 agent，不要越界自審。
- auditor 產出的是**候選 finding**，不是 finding。沒過階段 3 之前不得寫進報告。
- auditor **不驗證自己的產出**（`rules/false-positive.md` §1）。

---

## 階段 3 ｜ 對抗式驗證（finding-verifier）

每一條候選 finding 都要過。驗證者的立場是**證明這條是誤報**，證不倒才放行。

| 結果 | 去處 |
|---|---|
| 驗證通過 | 進報告的 Finding |
| 確認是誤報 | 丟掉；若「為什麼不是漏洞」不直觀 → 進「已排除項目」 |
| 驗不出來 | 進「待查清單」，**不給嚴重度、不算進統計** |

**這一階段不能省。** 省掉它，報告的可信度就沒了。

---

## 階段 4 ｜ 產出報告（report-writer）

依 `rules/report-standard.md` 組裝。交付前自檢：

- [ ] 每條 finding 的七個必備欄位齊全（`rules/evidence-discipline.md` §1）
- [ ] 每條 finding 的攻擊路徑從**對外入口**寫起
- [ ] 「修復方向」是具體改法，不是空話，且盡量對應 cx-sports-v2 自己的既有規範條文
- [ ] 報告中**沒有**真實憑證、可執行 payload、真實玩家資料（`rules/scope-safety.md` 紅線 3）
- [ ] 跨 repo 問題已獨立成章，未混入本次統計
- [ ] 待查清單、已排除項目、本次掃描限制三章都有寫
- [ ] 修復優先序依「嚴重度 × 修復成本」排，不是單純照嚴重度

---

## 三種掃描模式

| 模式 | 觸發 | 範圍 | 入口 |
|---|---|---|---|
| **全面掃描** | 「做一次資安掃描」 | 四階段全跑，九條軸全掃 | `/sec-scan` |
| **單軸快掃** | 「看一下權限有沒有問題」 | 精簡 recon + 指定軸 + 驗證 | `/sec-quick <軸>` |
| **回歸驗證** | 「修完了，再確認一次」 | 對照上次報告逐條複驗 | `/sec-verify <報告路徑>` |

> **模式紀律**：要快掃就不要擅自升級成全面掃描（7,808 個 Java 檔，燒 token 又拖時間）；
> 要全面掃描就不要只掃一條軸交差。

## OQ 與「要問使用者」的兩條硬規則

### 一、用國中生聽得懂的話寫

每一則 `⏳` OQ、以及每一個你要丟給使用者的問題，都必須讓**一個國中生讀完就能直接回你 A 或 B**。
做不到就是寫壞了，**重寫**，不要送出去。

**每則必含三段：**

| 段 | 寫什麼 |
|---|---|
| **情況** | 什麼時候、什麼狀況下會遇到這件事 |
| **卡住什麼** | 不決定的話，哪個功能／流程做不下去 |
| **選項** | 每個一句話 + 它的代價；傾向的那個後面標「（建議：一句理由）」 |

**禁止：**

| ❌ | 為什麼不行 |
|---|---|
| 只寫「OQ-5 未決，無法繼續」 | 看的人不知道 OQ-5 是什麼 |
| 用內部代號當問題本體（任務編號、章節號、模組名、函式庫名） | 那是我們的編號，不是問題 |
| 用技術名詞而不解釋（冪等、併發、接縫、契約、回歸） | 要用就當場用一句話說明白 |
| 沒有選項，只寫「請指示」 | 沒選項等於要對方從零想，那是我們的工作 |

> **反例**：「彩池瓜分的比例演算法與時間窗未定義」
> **正例**：「大獎被好幾個人同時中時，錢怎麼分？」＋ 情況 ／ 卡住什麼 ／ A、B、C 各自的代價

### 二、沒問題就不要硬生問題

送出之前先自問：**這題我能不能從需求、既有文件、或本範本的既有慣例，推出一個合理的預設？**

- **能** → **直接採用預設**，在產出裡用一句話寫明「我採了什麼、為什麼」，然後繼續做。**不要開 OQ。**
- **不能，而且不同答案會導向實質不同的工作** → 這才是真的 OQ，照第一條的格式寫。

> **為什麼**：問題本身有成本。把自己判斷得出來的事丟回去，等於把工作推回給對方；
> 而且會**稀釋真正需要拍板的那一題** —— 一次丟五個問題，重要的那個就被淹掉了。
> **湊數的 OQ 比沒有 OQ 更糟。**

> 兩條不衝突：第二條決定**要不要問**，第一條決定**問了怎麼寫**。
