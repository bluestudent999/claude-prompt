# spec-review — 規格預審

**強制使用的情形：**
- 改動任一推論參數或開盅判定（`rules/pipeline.md` §2）
- 改動 TCP 輸出契約或廣播接線（`rules/detector-contract.md`）
- 改動部署介面（CLI、埠、串流來源、打包清單）
- 新增管線能力（新輸出通道、無頭模式、新遊戲類型…）

**可跳過：** 純繪圖樣式、註解 / docstring、單一文案、設定值搬移、明確的 bug 修復（非辨識行為）。

---

## Phase A：需求釐清

對照 `rules/development-workflow.md` 的 6 欄位需求格式，把缺的標 `⏳`。

**辨識類需求的必問項（缺了無法定位）：**
- 哪一桌 / 哪個串流位址
- 什麼時間發生（好對照 `data/verified_rounds_sicbo/` 留存圖）
- 症狀是「沒反應」還是「點數錯」
- Go 端有沒有收到東西
- 有沒有截圖 / log / payload

---

## Phase B：Mental Model Check（≤100 字，先給使用者確認再往下）

**這一步 10 秒，可以換掉一份寫錯方向的 spec。** 必含三件事：

1. **現況真相（附 grep 證據）**
   例：「主程式目前未 import `TCPBroadcaster`（grep 零命中），開盅判定成立時只存驗證圖，不送 TCP」
2. **關鍵檔案與行號**
   例：「開盅判定在 `recognize_sicbo_stream.py:512`；廣播實作在 `tcp_broadcaster.py:70 send_dice_result`」
3. **鎖定的實作方向**
   例：「在 512 判定成立處呼叫 `send_dice_result(dice_values)`，`main()` 開頭 `start()`、所有退出路徑 `stop()`」

使用者回「方向錯了」→ **回 Step 0 重查，不要進 Phase C**。

> **本專案特有的坑：** 文件與程式碼有 9 項已知落差（`CLAUDE.md` §7）。Phase B 的「現況真相」**必須用 grep 驗證**，不能引用文件描述。

## Phase C：規格撰寫

寫入 `plan/YYYY-MM-DD_<功能名>_spec.md`：

```markdown
# <功能名> 規格

## §0 元資料
- 管線段別：<資料 / 訓練 / 晉升 / 推論 / 輸出 / 部署>
- l_tier：<L1 / L2 / L3>
- 涉及 Go 端契約：<是 / 否>
- 涉及部署介面（需同步 4 處）：<是 / 否>
- 對應已知落差：<CLAUDE.md §7 第 n 項 / 無>

## §1 現況（附證據）
| 陳述 | 證據 |
|------|------|
| 主程式未接廣播 | `grep -n "TCPBroadcaster" recognize_sicbo_stream.py` → 零命中 |

## §2 期望行為（可驗收）
- <使用者/Go 端能觀察到什麼具體變化>
- 反例：<什麼情況下**不應該**發生>

## §3 辨識行為定義（涉及推論時必填）
- 什麼算「有效偵測」：<顆數、信心度、面積>
- 什麼算「一次開盅」：<穩定條件、去重規則>
- 邊界情境：<4 顆怎麼辦？2 顆怎麼辦？點數超範圍怎麼辦？>

## §4 影響範圍
| 檔案 | 影響 |
|------|------|
| 文件同步需求 | `.plan/deployment_guide.md` / `start_recognize.*` / `pack_prod.sh` <需要 / 不需要> |

## §5 驗收條件
- [ ] <可觀察、可驗證的條目>
- [ ] 回放驗證：<用哪批影像、通過門檻>
- [ ] 契約 smoke：<收到合法 payload、一回合一次>

## §6 待決問題
- ⏳ <問題>：背景 / 為何要你決 / 選項 A B（**建議 A，因為…**）
```

## Phase D：邊界情境盤點（辨識類必做）

骰寶辨識的邊界情境很多，**spec 沒定義的，實作時就會被隨意決定**：

| 情境 | 必須在 §3 定義 |
|------|--------------|
| 偵測到 4 顆以上 | 取信心度最高的 3 顆？還是不開盅？ |
| 只偵測到 2 顆 | 等待？補值？（**補值等同造假，見 `detector-contract.md`**） |
| 兩顆骰子疊在一起 | IoU 去重會合併成一顆 → 變成 2 顆 → 不開盅 |
| 骰子在穩定期間被碰動 | `class_changed` 重置穩定計時 |
| 串流在開盅瞬間斷線 | 該局不送？重連後重數？ |
| 同一局判定兩次 | 去重旗標 |
| Go 端未連線時開盅 | 結果丟失（無緩衝）——這是可接受的嗎？ |

---

## Phase E：CONFIRM Gate

進 Step 2 規劃前必須**同時**滿足：

- [ ] 所有 ⏳ 已決議並回寫 spec
- [ ] 使用者**顯式** CONFIRM

> **沒有 ⏳ ≠ 自動通過。** 必須拿到明確的確認。

---

## Phase F：交棒

輸出給 planner：spec 路徑 + §0 元資料 + §5 驗收條件。planner 據此寫 §4 驗證計畫。

## 紀律

| ❌ | ✅ |
|---|---|
| 用文件描述當作現況 | **grep 驗證**，文件在本專案不可信 |
| 「辨識不準，調高信心度」當成規格 | 先定義「什麼算準」與「用什麼驗證」，再談手段 |
| 邊界情境留給實作時決定 | §3 明確定義，否則會被隨意決定 |
| 同時處理多項已知落差 | 一份 spec 一項 |
| 涉及 Go 端卻不標註 | §0 明確標出，讓使用者知道要協調對方 |
